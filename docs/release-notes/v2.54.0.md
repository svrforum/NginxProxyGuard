## 🛡️ WAF 규칙의 "부분 제외"가 이제 제대로 동작합니다

특정 경로 하나에서만 CRS 규칙을 끄는 기능이, 두 번째 경로를 추가하는 순간 아래 오류로 막혀 있었습니다.

```
A database error occurred
failed to get WAF rule exclusion: sql: expected 10 destination arguments in Scan, not 8
```

한 호스트의 한 규칙에 예외를 **하나라도 만들고 나면**, 그 규칙은 더 이상 손댈 수 없는 상태가 됐습니다. 이제 정상 동작합니다.

### 무엇이 달라지나

- **같은 규칙에 여러 경로를 등록할 수 있습니다.** `942370`을 `/api/a`에서 끄고, 따로 `/api/b`에서도 끌 수 있습니다. 완전히 같은 범위를 다시 등록할 때만 "이미 있음"으로 거절합니다.
- **부분 제외 하나만 해제해도 나머지가 남습니다.** 지금까지는 `/api/a`만 해제하려 해도 같은 규칙의 `/api/b`까지 **함께 삭제**됐습니다. 모르는 사이에 예외가 사라지던 동작입니다.
- **규칙 상태 표시가 실제와 맞습니다.** 경로 하나만 제외한 규칙은 나머지 모든 요청에서 여전히 동작하므로, 이제 **활성**으로 표시하고 `부분 제외 N개` 배지를 함께 보여줍니다. 예전에는 전체 비활성으로 보였습니다.
- **정책 관리 화면에서 부분 제외를 개별로 확인하고 해제**할 수 있습니다. 규칙 토글로 한 번에 되돌릴 때는 부분 제외도 함께 지워진다고 미리 알려 드립니다.

### 함께 바로잡은 것들

- **호스트 복제 시 예외 범위가 사라지던 문제.** 복제하면 `/api/a`에만 걸려 있던 예외가 **호스트 전체 비활성**으로 바뀌어, 복제한 호스트에서 해당 CRS 규칙이 모든 경로에서 꺼졌습니다.
- **부분 제외가 전역 비활성을 가리던 문제.** 어떤 규칙을 전역으로 끄셨는데 그 호스트에 부분 제외가 하나라도 있으면, 전역 설정이 그 호스트에만 적용되지 않았습니다.
- **백업 복원 시 범위 값 검증.** 복원은 범위 값을 검사하지 않고 그대로 ModSecurity 설정에 넣던 유일한 경로였습니다.
- **범위를 `/`로 지정하면 `이 호스트 전체`로 저장됩니다.** 모든 요청이 `/`로 시작하므로 사실상 호스트 전체 비활성인데 규칙은 활성으로 표시됐습니다. 이제 실제 의미대로 기록되고 그렇게 표시됩니다.
- **예전 버전이 만든 예외의 상태 표시.** `scope_type`이 비어 있는 오래된 행(구버전 복제가 만들던 형태)을 부분 제외로 잘못 읽어, 규칙이 실제로는 호스트 전체에서 꺼져 있는데 **활성으로 표시**됐습니다.
- **손상된 예외가 있어도 백업 복원이 중단되지 않습니다.** 범위 값을 해석할 수 없는 행 하나 때문에 복원 전체가 롤백돼 프록시 호스트·인증서까지 되돌아갈 수 있었습니다. 이제 그 행만 건너뛰고 로그로 알려 드리며, 해당 규칙은 **보호 상태를 유지**합니다.
- **`rule_id` 범위 검증.** 규칙 번호도 같은 ModSecurity 설정에 들어가는데 검증이 없어, 잘못된 값이 들어가면 이후 모든 nginx 재적용이 막힐 수 있었습니다.
- **API 명세 정정.** `scope_type`·`scope_value`가 명세에 아예 없어서, 명세로 만든 클라이언트는 호스트 전체 비활성만 만들 수 있었습니다.

## 🐛 드물게 DB 조회가 멈추던 문제

v2.51.0~v2.53.0은 Go 1.27.0으로 빌드됐는데, 이 버전의 `database/sql`에 조회 반복 중 연결이 끊기거나 시간이 초과되면 **영구히 멈출 수 있는** 결함이 있었습니다. 애플리케이션이 피해 갈 방법이 없는 종류라, Go 1.27.1로 올려 해결했습니다.

## 🛡️ Partial WAF rule exclusions actually work now

Switching a CRS rule off for a single path worked once. Adding a second path failed with:

```
A database error occurred
failed to get WAF rule exclusion: sql: expected 10 destination arguments in Scan, not 8
```

Once a host had **any** exclusion on a rule, that rule could not be touched again. Fixed.

### What changes

- **Several paths per rule.** You can exempt `942370` under `/api/a` and, separately, under `/api/b`. Only an identical scope is refused as a duplicate.
- **Removing one exemption keeps the rest.** Removing `/api/a` used to delete `/api/b` on the same rule as well — exemptions disappeared without anyone asking.
- **Rule status now matches reality.** A rule exempted on one path still protects every other request, so it now shows as **enabled** with a `N partial exclusions` badge. It used to show as fully disabled.
- **The policy screen lists partial exclusions and removes them individually.** Re-enabling the whole rule with the toggle warns first that the partial exclusions go too.

### Also corrected

- **Host clone dropped the scope.** Cloning turned an exemption scoped to `/api/a` into a host-wide one, switching that CRS rule off everywhere on the cloned host.
- **A partial exclusion masked the global one.** If you disabled a rule globally, hosts holding any narrow exemption for it never received the global setting.
- **Backup restore now validates scope values.** It was the one write path that put a value into a ModSecurity directive unchecked.
- **A scope of `/` is now stored as the host scope.** Every request starts with `/`, so it disabled the rule host-wide while still reporting the rule as enabled. It is now recorded — and shown — as what it actually is.
- **Status of exclusions written by older versions.** Rows with an empty `scope_type` (the shape the old clone path produced) were read as narrow exemptions, so a rule that was in fact switched off for the whole host **reported as enabled**.
- **A corrupt exclusion no longer aborts a backup restore.** One row with an unreadable scope could roll the whole restore back, taking proxy hosts and certificates with it. That row is now skipped with a log line, and the rule **keeps protecting** the host.
- **`rule_id` is now range-checked.** The rule number goes into the same ModSecurity file as the scope; an out-of-range value could leave every later nginx reload blocked.
- **API specification corrected.** `scope_type` and `scope_value` were absent from the spec entirely, so a spec-generated client could only ever create host-wide exclusions.

> Thanks to **@Messier333**, whose report pinned the exact function and column mismatch. (#286)

## 🐛 A rare permanent stall in database queries

v2.51.0–v2.53.0 were built on Go 1.27.0, whose `database/sql` could deadlock permanently when a query's row iteration raced its own context timeout or a client disconnect. There is no application-level way around it, so the toolchain moves to Go 1.27.1.

It is not frequent, but a query that hits it never finishes — upgrading is worthwhile.
