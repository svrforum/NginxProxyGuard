## 🔑 SSO — 그룹에서 제외된 사용자의 권한이 이제 확실히 회수됩니다

### ⚠️ 업그레이드 전에 확인해 주세요

**SSO 공급자에 "그룹 → 역할 매핑"을 쓰면서 "기본 역할"을 비워 두셨다면, 업그레이드 전에 기본 역할을 지정해 주세요.** 그렇지 않으면 매핑에 걸리지 않는 사용자는 로그인이 거부됩니다.

무엇이 문제였는지부터 말씀드립니다. IdP(Authelia, Authentik, Keycloak 등)에서 어떤 사용자를 관리자 그룹에서 **빼도**, NPG는 그 사용자가 예전에 받았던 역할을 그대로 유지한 채 로그인시켰습니다. 기본 역할이 지정돼 있으면 그쪽으로 강등됐지만, 비워 둔 경우에는 **권한 회수가 아무 효과가 없었습니다.** 관리자 그룹에서 제외된 사람이 계속 관리자로 들어올 수 있었다는 뜻입니다.

이제 이렇게 동작합니다.

| IdP가 보낸 그룹 정보 | 동작 |
|---|---|
| 매핑에 일치하는 그룹 있음 | 매핑된 역할 적용 |
| 일치 없음 + **기본 역할 있음** | 기본 역할로 강등 |
| 일치 없음 + **기본 역할 없음** | **로그인 거부** (새 동작) |
| 그룹 정보가 아예 안 옴 | 기존 역할 유지 (아래 설명) |

**"그룹 정보가 안 온 것"과 "그룹에서 빠진 것"을 구분합니다.** 일부 공급자(Authelia 등)는 그룹을 UserInfo 엔드포인트로만 내려주는데, 그 조회가 일시적으로 실패했다고 해서 권한을 회수하면 잠깐의 장애가 영구적인 권한 변경이 됩니다. 그래서 **그룹 정보가 오지 않은 경우에는 아무것도 바꾸지 않고** 기존 역할을 유지한 뒤 경고만 남깁니다. 참고로 지금까지는 이 경우에 **기본 역할로 강등**해 버렸는데, 그 문제도 함께 고쳐졌습니다.

**로그인이 거부되면 이렇게 푸시면 됩니다.** 설정 → SSO에서 해당 공급자의 **기본 역할**을 지정하거나(가장 권한이 낮은 역할을 권장), IdP 쪽 그룹 매핑을 바로잡으면 됩니다. 관리자 계정 자체가 막힌 경우에도 로컬 로그인은 항상 살아 있고, 그마저 어려우면 다음 명령으로 복구할 수 있습니다.

```bash
docker compose exec api ./server reset-password
```

> SSO로 자동 생성된 계정은 로컬 비밀번호가 없으므로, 그런 계정만 쓰고 계신다면 업그레이드 전 기본 역할 지정을 특히 권합니다.

## 🔁 예전에 저장된 위험한 리다이렉트를 이제 끌 수 있습니다

구버전에서 저장된 리다이렉트 호스트 중에는 지금 기준으로는 안전하지 않은 값(예: 전달 경로에 nginx 변수가 들어간 경우)이 남아 있을 수 있습니다. 그런 항목은 **비활성화조차 되지 않았습니다.** 저장할 때 전체 값을 다시 검사하는데, 기존 값이 검사를 통과하지 못해 "끄기"까지 막혀 버렸기 때문입니다. 삭제 권한이 없는 운영자는 위험한 설정을 즉시 내릴 방법이 없었습니다.

이제 **끄는 것만 하는 변경은 허용**됩니다. 값을 그대로 두고 비활성화하면 저장되고, 해당 nginx 설정이 제거됩니다. 값을 실제로 바꾸려 하거나 비활성화된 항목을 다시 켜려 하면 예전처럼 거부되므로, 위험한 설정이 되살아나는 일은 없습니다.

거부될 때의 안내도 좋아졌습니다. 지금까지는 값이 거부되면 "데이터베이스 오류"로 표시됐지만, 이제 **어떤 항목이 왜 거부됐는지** 알려 줍니다.

## 🔑 SSO — revoking a group now actually revokes the role

### ⚠️ Please check this before upgrading

**If your SSO provider uses group-to-role mappings but has no default role set, set one before upgrading.** Otherwise users whose groups match no mapping will be denied sign-in.

Here is what was wrong. When you removed someone from an admin group at your IdP (Authelia, Authentik, Keycloak…), NPG kept the role they had been granted earlier and signed them in anyway. With a default role configured they were demoted to it — but with the field left empty, **revoking the group had no effect at all.** Someone removed from the admin group could keep signing in as an admin.

The behavior now:

| Groups the IdP sent | Result |
|---|---|
| Matches a mapping | Mapped role applied |
| No match + **default role set** | Demoted to the default role |
| No match + **no default role** | **Sign-in denied** (new) |
| No groups sent at all | Existing role kept (see below) |

**"No groups were sent" and "removed from the group" are now told apart.** Some providers (Authelia among them) serve groups only from the UserInfo endpoint, and treating a temporary lookup failure as a revocation would turn a brief outage into a permanent privilege change. So when no group claim arrives, **nothing changes** — the existing role is kept and a warning is logged. Previously this case **demoted the user to the default role**, which is fixed too.

**If a sign-in is denied**, set a **default role** for that provider under Settings → SSO (a least-privilege role is the right choice), or fix the group mapping at your IdP. Local sign-in always remains available, and if you are fully locked out:

```bash
docker compose exec api ./server reset-password
```

> Accounts created automatically by SSO have no local password, so if those are all you use, setting a default role before upgrading is strongly recommended.

## 🔁 Unsafe legacy redirects can finally be switched off

Redirect hosts saved by older versions may hold values today's validation rejects — an nginx variable in the forward path, for example. Those entries **could not even be disabled**: saving re-validates the whole record, and the stored value failed, so "turn it off" was refused along with everything else. An operator without delete permission had no way to take a risky entry down.

**A change that only disables an entry is now allowed.** Leave the values as they are, switch it off, and it saves — the nginx config for it is removed. Actually editing a value, or re-enabling a disabled invalid entry, is still rejected, so nothing unsafe comes back to life.

Rejections read better now, too: a refused value used to surface as "a database error", and now names the field and the reason.
