## 🛡️ Bug Fixes — System Logs on cold start

Follow-up to #205, fixing two issues (#207) that left the **System Logs** view sparse right after `docker compose up` until you restarted every container.

- **No more bogus "No such container" error rows.** The log collector runs inside the **API** container, which starts before the containers that depend on it (`ui`, `nginx`). Its first `docker logs` attach therefore raced their creation, and docker's own `Error response from daemon: No such container` message was being ingested as an *error*-level log entry — inflating the error count and cluttering the view. The collector now waits for a container to exist before attaching (the retry loop re-checks every few seconds).

- **Container startup logs now appear on a cold start.** The `db` and `ui` sources default to a `warn` minimum level, which hid their `info`/`notice` startup lines (e.g. *"database system is ready to accept connections"*, nginx worker start) even once the burst was captured. A short startup-grace window now lets info-level boot logs through so you can watch your stack come up; steady-state noise stays filtered afterwards.

> ⚠️ **The log collector lives in the API image.** To get this fix, pull and recreate the **api** container (not just nginx):
> ```bash
> docker pull svrforum/nginxproxyguard-api:2.32.1
> docker compose up -d
> ```
