## 🔐 Authentik ForwardAuth 로그인이 되지 않던 문제

### 익스플로잇 차단이 Authentik 로그인 화면으로 가는 길을 막고 있었습니다

프록시 호스트에 **Authentik ForwardAuth**를 연결하고 **익스플로잇 차단(Block Exploits)** 을 켜 두셨다면, 보호된 주소에 접속했을 때 로그인 화면 대신 **403**이 떴습니다. 두 기능 모두 기본값이 켜짐이라, 조합을 만들면 바로 재현되는 상태였습니다.

원인은 NPG 자신이 만든 주소였습니다. 미인증 요청을 Authentik으로 보낼 때 NPG는 원래 주소를 `?rd=https://...` 형태로 붙여 주는데, 내장 차단 규칙 중 **"URL Parameter Injection (RFI)"** 이 정확히 `이름=https://` 패턴을 막습니다. 그리고 이 검사는 개별 경로보다 **먼저** 도는 자리에 있어서, Authentik 전용 경로를 따로 두었는데도 그 앞에서 잘렸습니다.

Authelia는 리다이렉트 주소를 Authelia 쪽이 만들어 주기 때문에 같은 문제가 없었습니다.

이제 NPG가 그 주소를 만들 때 `://` 를 인코딩해서 넘깁니다. 차단 규칙은 그대로 두었고, Authentik이 받는 값도 이전과 같습니다.

**이미 `^/outpost.goauthentik.io` 를 익스플로잇 예외에 넣어 두셨다면 지우셔도 됩니다.** 그 예외는 해당 경로의 검사를 통째로 건너뛰게 하므로, 없는 편이 안전합니다.

> 제보해 주신 **@four2mis** 님 감사합니다. (#265)

## 🔁 표준이 아닌 포트를 쓰면 리다이렉트에 내부 포트가 새던 문제

**공유기에서 443을 다른 포트(예: 18443)로 넘겨 NPG를 운영하는 구성**에서, NPG가 만든 리다이렉트 주소에 **밖에서는 닿을 수 없는 내부 포트**가 붙었습니다. 브라우저가 그 주소를 따라가면 그대로 멈췄습니다.

nginx는 상대 경로 리다이렉트를 절대 주소로 바꿔 줄 때 **자기가 듣고 있는 포트**를 붙입니다. 브라우저가 보낸 주소에는 포트가 없었는데도 nginx가 스스로 `:18443` 을 채워 넣은 것입니다.

Authentik 로그인 리다이렉트에서 처음 발견됐지만 거기에 한정된 문제가 아니었습니다. **지오 차단 챌린지 화면, 그리고 백엔드가 보내온 리다이렉트를 NPG가 다시 써 주는 모든 프록시 호스트**가 같은 영향을 받았습니다.

이제 리다이렉트 주소를 상대 경로 그대로 내보냅니다. 브라우저가 현재 주소를 기준으로 알아서 완성하므로, 밖에서 들어온 접속에는 포트가 붙지 않고 **LAN에서 `:18443` 으로 직접 접속하던 경우에는 그 포트가 그대로 유지**됩니다.

**임시 조치로 전역 설정의 `custom_http_config` 에 `absolute_redirect off;` / `port_in_redirect off;` 를 넣어 두셨다면 반드시 지워 주세요.** 이제 NPG가 `absolute_redirect off` 를 직접 내보내므로 같은 지시어가 남아 있으면 설정 검사가 중복 오류로 실패하고, `port_in_redirect off;` 는 포트로 직접 접속하는 경로를 계속 깨뜨립니다.

> 제보해 주신 **@four2mis** 님 감사합니다. (#264)

## 🚦 Rate Limit 예외 IP가 이번 버전부터 실제로 동작합니다

**솔직하게 말씀드립니다: Rate Limit의 "예외/화이트리스트 IP" 항목은 지금까지 어떤 버전에서도 동작한 적이 없습니다.** 값은 저장되고, 화면에도 보이고, 백업에도 들어갔지만, nginx 설정으로는 한 번도 렌더링되지 않았습니다. 전역 기본값과 호스트별 설정 모두 마찬가지였습니다.

이번 버전부터 등록하신 IP와 대역(CIDR)이 **정말로 rate limit에서 면제됩니다.** 쉼표·줄바꿈 어느 쪽으로 구분해도 되고, `10.1.2.3/8` 처럼 쓴 대역은 `10.0.0.0/8` 로 알아서 정규화되며, `# 메모` 를 뒤에 붙여도 됩니다.

함께 고친 것들입니다.

- **저장할 때 검증합니다.** IP나 CIDR이 아닌 값은 400으로 거절하고 어떤 값이 문제인지 알려 줍니다. 이전 버전에서 저장된 잘못된 값이 있어도 설정 생성 시 건너뛰므로 nginx가 멈추는 일은 없습니다.
- **호스트별 예외 목록을 비울 수 있게 됐습니다.** 지금까지는 한 번 저장하면 화면에서 지워도 저장소에는 옛 값이 되살아나, 사실상 지울 수 없었습니다.
- 전역 Rate Limit 설정에서 다른 항목만 바꿀 때 예외 목록이 조용히 사라지던 문제도 함께 고쳤습니다.

**확인 부탁드립니다.** 예외 IP를 등록해 두셨던 분은, 그 주소들이 지금까지는 제한을 받고 있었고 **업그레이드 후부터 정말로 면제됩니다.** 목록에 남아 있는 값이 지금도 의도에 맞는지 한 번 살펴봐 주세요. 참고로 이 목록은 클라이언트가 신고하는 주소(X-Forwarded-For 반영 후)를 기준으로 하므로, 내부망에서 헤더를 위조할 수 있는 환경이라면 신뢰 경계 안에서만 사용하시길 권합니다.

> #258 을 조사하는 과정에서 발견해 별도 이슈로 분리한 건입니다. (#263)

## 🔑 관리 패널이 자기 자신을 잠그던 문제

**NPG 관리 화면을 NPG 자신을 통해 프록시로 운영하는 구성**에서, 패널을 몇 번 오가다 보면 갑자기 429가 쏟아지고 심하면 **로그인 화면에서 "Rate limit exceeded"가 떠 로그인 자체가 막혔습니다.**

원인은 프록시 호스트의 rate limit이 아니라 **NPG API 자체의 IP당 분당 100회 제한**이었습니다. 호스트 목록은 행마다 상태 확인 요청을 보내고 서른 개 가까운 화면이 주기적으로 갱신 요청을 보내니, 패널 혼자서 예산을 다 써 버립니다. 그리고 로그인 요청까지 같은 예산을 쓰고 있어서, 예산이 바닥나면 다시 들어올 방법이 없었습니다.

이렇게 바뀝니다.

- **로그인은 별도 예산을 씁니다.** 패널이 아무리 바빠도 로그인 화면은 막히지 않습니다.
- 일반 API 예산은 IP당 분당 **100 → 600** 으로 올렸습니다. 패널이 정상 사용으로 도달할 수 없는 수준입니다.
- 필요하면 `.env` 에서 조정할 수 있습니다: `API_RATE_LIMIT_PER_MINUTE` (0이면 끔), `AUTH_RATE_LIMIT_PER_MINUTE`. 로그인 쪽은 무차별 대입을 막는 브레이크이므로 낮게 유지하시길 권합니다.
- API가 보내는 429 응답에 이것이 **NPG API 자체의 제한**이라는 표시(`code: "api_rate_limit"`)를 넣었습니다.

**로그 화면의 "Rate Limit" 라벨도 정확해졌습니다.** 지금까지는 백엔드 애플리케이션이 돌려준 429까지 전부 "Rate Limit"으로 표시해서, 이번 건처럼 원인을 엉뚱한 곳에서 찾게 만들었습니다. 이제 nginx가 직접 차단한 요청(업스트림에 도달하지 않은 429)만 그렇게 표시합니다. 이미 기록된 과거 로그의 라벨은 바뀌지 않습니다.

> 스크린샷과 함께 끈질기게 확인해 주신 **@ydrob** 님 감사합니다. (#258)

## 🔐 Authentik ForwardAuth logins were failing

### Exploit blocking was blocking the path to Authentik's own login page

If you attached **Authentik ForwardAuth** to a proxy host and left **Block Exploits** on, visiting a protected address returned **403** instead of the login page. Both settings default to on, so the combination alone reproduced it.

The address NPG itself generates was the cause. When handing an unauthenticated request to Authentik, NPG appends the original address as `?rd=https://...` — and one of the built-in rules, **"URL Parameter Injection (RFI)"**, blocks exactly the `name=https://` shape. That check runs *before* individual paths are matched, so the dedicated Authentik path never got a chance.

Authelia was unaffected because Authelia builds that redirect address itself.

NPG now encodes the `://` when it builds the address. The blocking rule is unchanged, and what Authentik receives is unchanged.

**If you already added `^/outpost.goauthentik.io` to your exploit exceptions, you can remove it.** That exception skips exploit checking for the path entirely, so you are safer without it.

> Thanks to **@four2mis** for the report. (#265)

## 🔁 A non-standard port leaked into redirect URLs

If you run NPG behind a router that forwards **443 to a different port** (18443, for example), redirects NPG produced carried an **internal port that is not reachable from outside**. Browsers following them just hung.

When nginx turns a relative redirect into an absolute address, it appends **the port it is listening on**. Even though the browser's own address had no port in it, nginx filled in `:18443` by itself.

It surfaced on the Authentik login redirect, but it was never limited to that. The **geo-blocking challenge page, and every proxy host where NPG rewrites a redirect coming back from the backend**, were affected the same way.

Redirect addresses are now emitted as relative paths. The browser completes them against the address it is already on — so requests arriving from outside get no port, while **a LAN client that really did connect on `:18443` keeps that port**.

**If you worked around this with `absolute_redirect off;` / `port_in_redirect off;` in `custom_http_config`, you must remove it.** NPG now emits `absolute_redirect off` itself, so a duplicate line fails the config test — and a leftover `port_in_redirect off;` keeps direct-by-port access broken.

> Thanks to **@four2mis** for the report. (#264)

## 🚦 Rate limit exception IPs actually work now

**Being honest with you: the rate limit "exception / whitelist IPs" field has never worked, in any version.** The value was stored, shown in the UI and carried through backups — but it was never rendered into nginx configuration. That was true for both the global default and per-host overrides.

From this version, the IPs and CIDR ranges you register are **genuinely exempt from rate limiting.** Commas and newlines both work as separators, a range written as `10.1.2.3/8` is normalized to `10.0.0.0/8`, and a trailing `# note` is allowed.

Fixed along the way:

- **Values are validated on save.** Anything that is not an IP or CIDR is rejected with a 400 that names the offending entry. Invalid values saved by earlier versions are skipped at config-generation time, so they cannot break nginx.
- **Per-host exception lists can finally be cleared.** Until now, once saved, clearing the field brought the old value back — it was effectively permanent.
- Updating other fields of the Global Rate Limit no longer silently wipes the exception list.

**Please check your list.** If you had exception IPs registered, those addresses were being rate-limited all along and become genuinely exempt after upgrading. Also note the list matches the client address after X-Forwarded-For processing, so treat it as trustworthy only within your network's trust boundary.

> Found while investigating #258 and split out separately. (#263)

## 🔑 The admin panel could lock itself out

If you proxy the **NPG admin panel through NPG itself**, a busy session could suddenly return a wall of 429s — and at worst, the login screen showed "Rate limit exceeded" and **you could not sign back in.**

The cause was not a proxy host rate limit but **NPG's own API limit of 100 requests per minute per IP.** The host list probes every row, nearly thirty screens poll on timers — the panel spends that budget by itself. And because login shared the same budget, once it was gone there was no way back in.

What changes:

- **Signing in has its own budget.** However busy the panel is, the login screen stays reachable.
- The general API budget rose from **100 to 600 per minute per IP** — beyond what the panel can reach through normal use.
- Both are tunable in `.env`: `API_RATE_LIMIT_PER_MINUTE` (0 disables), `AUTH_RATE_LIMIT_PER_MINUTE`. Keep the auth one low; it is a brake on credential stuffing.
- The API's 429 response now identifies itself (`code: "api_rate_limit"`) so it can no longer be mistaken for a proxy host rate limit.

**The log viewer's "Rate Limit" label is accurate now, too.** It used to tag every 429 that way — including ones returned by your backend application — which is exactly what sent this investigation in the wrong direction at first. Now only requests nginx itself blocked (429 with no upstream) get the label. Already-recorded rows keep their old label.

> Thanks to **@ydrob** for the persistent, screenshot-backed follow-up. (#258)
