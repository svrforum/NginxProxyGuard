## 🔑 SSO

### Authentik 2025.10 이후 계정 연결이 막히던 문제

Authentik을 **2025.10 이상**으로 올리셨다면 SSO로 기존 계정에 로그인이 안 되고 로그에 이렇게 남았을 것입니다.

```
SSO: no account for provider "authentik" — email present=true, verified=false
```

**NPG 버그가 아니라 Authentik의 의도적 변경입니다.** 기본 `email` 스코프 매핑이 보내는 값이 바뀌었습니다.

| Authentik 버전 | 기본값 |
|---|---|
| 2025.8 | `email_verified: True` |
| **2025.10 이상** | **`email_verified: False`** |

Authentik 측 이유도 타당합니다 — 관리자가 임의 이메일로 사용자를 만들 수 있는데 "검증됨"이라고 단언하는 건 위험하다는 것입니다. 같은 변경으로 Audiobookshelf, ODK Central, Grist도 같은 시기에 영향을 받았습니다.

NPG는 기존 계정에 SSO를 연결할 때 **검증된 이메일**을 요구합니다. 공급자에서 아무 주소나 등록할 수 있는 사람이 남의 NPG 계정을 가져가는 것을 막기 위해서입니다.

**해결 방법은 두 가지입니다.**

**1. Authentik에서 고치기 (권장)**
Customization → Property Mappings에서 **새 Scope Mapping**을 만들고(Scope name: `email`), 아래 식을 넣은 뒤 provider의 Advanced protocol settings에서 기본 매핑 **대신** 선택하세요.
```python
return {
    "email": request.user.email,
    "email_verified": True,
}
```
기본 매핑을 직접 고치면 업그레이드 때 원복되니 반드시 새로 만드셔야 합니다.

**2. NPG에서 이 공급자를 신뢰하기 (이번에 추가)**
설정 → SSO → 해당 공급자에 **"이 공급자의 이메일 주소를 신뢰"** 가 생겼습니다. 켜면 검증 표시 없이도 기존 계정과 연결됩니다.

기본값은 **꺼짐**이고, 켜기 전에 아래를 확인해 주세요.

> 이 공급자와 사용자 등록 과정을 **직접 통제할 때만** 켜세요. 그곳에서 임의의 이메일로 계정을 만들 수 있는 사람은, 같은 주소를 쓰는 NPG 계정으로 로그인할 수 있게 됩니다.

### 거절 이유를 로그에서 구분할 수 있습니다

`verified=false` 한 가지로 보이던 것이 두 가지로 나뉩니다. 조치가 서로 다르기 때문입니다.

- `false (the provider said so)` — 공급자가 미검증이라고 보냄 → 위 두 방법 중 하나
- `false (no email_verified claim was sent…)` — 클레임 자체가 없음 → 공급자 스코프 설정 확인

로그에 **버전도 함께** 찍힙니다(`SSO[2.41.0]: …`). 어떤 빌드에서 나온 로그인지 바로 알 수 있습니다.

> 로그를 정확히 보내 주신 **@heygoodluck** 님 감사합니다. 덕분에 원인을 특정할 수 있었습니다. (#248)

> ```

## 🔑 SSO

### Account linking broke after Authentik 2025.10

If you upgraded Authentik to **2025.10 or later**, signing in to an existing account through SSO stopped working, with this in the log:

```
SSO: no account for provider "authentik" — email present=true, verified=false
```

**This is not an NPG bug — it is a deliberate change in Authentik.** Its default `email` scope mapping now sends a different value:

| Authentik version | Default |
|---|---|
| 2025.8 | `email_verified: True` |
| **2025.10 and later** | **`email_verified: False`** |

Their reasoning is sound: an administrator can create users with arbitrary email addresses, so asserting that those addresses are verified is unsafe. The same change affected Audiobookshelf, ODK Central and Grist in the same week.

NPG requires a **verified** email before linking an SSO identity to an existing account, so that nobody who can register an arbitrary address at the provider can take over someone else's NPG account.

**There are two ways forward.**

**1. Fix it in Authentik (recommended)**
Under Customization → Property Mappings, create a **new Scope Mapping** (Scope name: `email`) with the expression below, then select it on your provider's Advanced protocol settings **in place of** the default.
```python
return {
    "email": request.user.email,
    "email_verified": True,
}
```
Editing the built-in mapping does not last — it is reverted on upgrade — so create a new one.

**2. Trust the provider from NPG (new in this release)**
Settings → SSO → your provider now has **"Trust this provider's email addresses"**. With it on, linking accepts the address without a verification flag.

It defaults to **off**, and before turning it on:

> Only enable this if you control the provider and how users enrol there. Anyone able to set an arbitrary email address on it can then sign in as the NPG account holding that address.

### The log now says which kind of refusal it was

What used to read as a single `verified=false` is now two distinct cases, because they need different fixes:

- `false (the provider said so)` — the provider reported the address as unverified → use one of the two options above
- `false (no email_verified claim was sent…)` — the claim never arrived → check the provider's scope configuration

The log line also carries the version now (`SSO[2.41.0]: …`), so a pasted log says which build produced it.
