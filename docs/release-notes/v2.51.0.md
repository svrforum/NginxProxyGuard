## 🌐 Cloudflare 프록시 뒤에서 국가 차단이 오작동하던 문제

Cloudflare 프록시(오렌지 클라우드)나 다른 CDN·리버스 프록시를 NPG 앞에 두면, **접속자의 IP가 아니라 그 프록시의 IP가 기록**됐습니다. 국가 차단을 켜 두셨다면 Cloudflare 서버의 국가로 판정되어 정상 방문자가 막혔습니다.

원인은 NPG가 신뢰할 프록시 목록을 **사설망 주소로만 고정**해 두고, 늘릴 방법을 제공하지 않았기 때문입니다.

### 설정 → 신뢰 프록시

목록을 직접 지정하실 수 있습니다.

- **Cloudflare 프리셋** — 체크 한 번으로 Cloudflare가 공개한 대역 22개가 들어갑니다.
- **직접 입력** — 다른 CDN이나 사무실 프록시 등을 IP·CIDR로 추가합니다.
- **실제 IP 헤더** — 기본값은 지금까지와 같은 `X-Forwarded-For`입니다.

**Cloudflare Tunnel만 쓰고 계시다면 이 설정은 필요 없습니다.** 터널은 이미 실제 IP가 올바르게 전달됩니다. 프록시 모드로 NPG를 직접 노출하신 경우에만 해당됩니다.

### ⚠️ 헤더를 바꾸실 때 주의할 점

`CF-Connecting-IP` 같은 헤더로 바꾸면, **그 헤더가 없는 요청은 실제 IP를 알 수 없게 됩니다.** NPG 앞에 공유기나 다른 프록시(HAProxy, 시놀로지, 또 다른 nginx 등)도 함께 있다면 그쪽 트래픽이 사설 IP로 기록되어 **국가 차단에 전부 걸릴 수 있습니다.** Cloudflare만 앞에 있는 경우에만 바꿔 주세요. 화면에도 같은 경고를 띄웁니다.

### 안전장치

신뢰 범위를 넓게 잡으면 방문자가 자기 IP를 마음대로 위장할 수 있고, 그러면 국가 차단·접근 목록·IP 차단·fail2ban·요청 수 제한이 **한꺼번에** 무력화됩니다. 그래서 목록이 감당하는 **전체 주소 개수**에 상한을 두고, 초과하면 이유와 함께 거절합니다. `0.0.0.0/0` 같은 값은 물론이고, `/8` 대역 256개를 나열해 인터넷 전체를 신뢰시키는 우회도 막힙니다.

사설망·루프백 대역은 **항상 신뢰**하며 제거할 수 없습니다. 도커 내부 통신과 LAN 프록시가 여기에 의존합니다. 내부 프록시가 `10.0.0.0/8` 같은 사설 대역에 있다면 직접 입력에 넣으셔도 됩니다 — 인터넷에서 보낼 수 없는 주소라 위 상한에 걸리지 않습니다.

> **이 설정을 건드리지 않으시면 동작이 전혀 달라지지 않습니다.** 생성되는 nginx 설정이 이전과 바이트 단위로 동일합니다.

> 신뢰 프록시를 켜신 뒤에는 **차단 IP 목록을 한 번 확인해 주세요.** 이 문제를 우회하려고 Cloudflare 서버 주소를 신뢰 IP나 차단 목록에 넣어 두셨다면, 이제 그 주소로 들어오는 요청이 없으므로 해당 항목은 의미가 없어집니다.

> **이름이 비슷한 다른 설정과 헷갈리지 않도록** — 이 화면은 **프록시된 트래픽**(GeoIP·접근 목록·차단 IP·fail2ban·요청 제한)에 적용됩니다. NPG 관리 화면 자체의 로그인 잠금과 API 토큰 IP 제한에 쓰이는 `TRUSTED_PROXY_CIDR` 환경변수와는 별개입니다.

## 🔢 로그 뷰어에서 상태 코드를 직접 입력할 수 있습니다

상태 코드 필터가 **17개 고정 버튼**뿐이라, nginx가 실제로 남기는 `499`나 `444`는 **아예 고를 수 없었습니다.**

이제 세 가지 방법을 함께 쓰실 수 있습니다.

- **분류 선택** — `2xx`, `4xx` 같은 단위로 한 번에
- **자주 쓰는 코드** — 버튼으로 바로
- **직접 입력** — `499`, `444`, `4xx` 등 무엇이든. 쉼표로 여러 개를 붙여 넣어도 됩니다

**제외 필터에도 상태 코드가 추가됐습니다.** 지금까지 IP·User-Agent·URI·호스트·국가만 제외할 수 있었는데, 이제 `200`이나 `3xx`를 빼고 보실 수 있습니다.

오타는 저장 시점에 알려 드립니다. 예전에는 잘못된 값이 조용히 무시되어, 필터가 걸린 것처럼 보이지만 실제로는 전체 목록이 나오는 상태가 됐습니다.

> 오류 로그는 상태 코드가 없으므로 코드를 제외하셔도 계속 표시됩니다. 그리고 **WAF에 차단된 요청은 403**이므로, 403을 제외하면 함께 숨겨집니다.

> 세 가지를 정리해 제안해 주신 **@iamxail** 님 감사합니다. (#278)

## 🚪 IP 직접 접속 차단(444)이 실제로 444를 돌려줍니다

**설정 → IP 직접 접속 처리**를 "연결 종료(444)"로 두셨는데도 로그에 **400**이 섞여 보이던 문제입니다.

가장 많았던 원인은 **HTTPS 포트로 들어온 평문 HTTP**입니다. 브라우저나 스캐너가 `https` 포트에 `http`로 붙는 경우인데, nginx가 이걸 본문 처리 단계 **이전에** 끝내 버려서 설정해 두신 444 규칙이 실행될 기회조차 없었습니다. 한 설치 기준 **일주일 400건 중 52%**가 이 경우였습니다.

이제 이런 요청도 **똑같이 연결을 끊습니다.**

> **의도적으로 바꾸지 않은 것들**
> - **요청 자체가 깨진 경우는 계속 400입니다.** 요청 라인이 깨졌거나 Host 헤더가 없으면 nginx는 Host를 읽기도 전에 거절하므로, 이때 연결을 끊어 버리면 **실제로 등록하신 도메인으로 온 요청까지** 소리 없이 끊기게 됩니다. 라이브러리 버그로 잘못된 요청을 보내는 정상 클라이언트가 원인을 알 수 없게 되므로, 진단 가능한 400을 남겨 두었습니다. 이런 요청은 대부분 스캐너 노이즈이고 로그에는 그대로 보입니다
> - **"403 반환"으로 두신 경우는 그대로입니다.** 프로토콜 쓰레기에까지 10KB짜리 안내 페이지를 돌려주면 응답이 요청의 70배가 넘어 반사 공격에 악용될 수 있습니다
> - **"웰컴 페이지 표시"도 그대로입니다** — 아무것도 막지 않기로 하신 설정이므로 nginx 기본 동작을 유지합니다

또한 **HTTPS로 IP 직접 접속**은 TLS 단계에서 거부되므로 애초에 HTTP 상태 코드가 남지 않습니다. 로그에 아무것도 안 보이는 것이 정상입니다. 이 내용을 설정 화면 안내에도 적어 두었습니다.

> 로그를 꼼꼼히 확인해 알려 주신 **@re-birkin** 님 감사합니다. (#280)

## 🌐 Country blocking misfired behind a Cloudflare proxy

With Cloudflare's proxy (orange cloud) — or any CDN or reverse proxy — in front of NPG, the address recorded for a request was **the proxy's, not the visitor's**. With country restriction enabled, requests were judged by Cloudflare's country and legitimate visitors were blocked.

The cause: NPG's list of proxies to trust for real-IP extraction was **hardcoded to private networks**, with no way to extend it.

### Settings → Trusted Proxies

You can now name the proxies you trust.

- **Cloudflare preset** — one click adds Cloudflare's 22 published ranges.
- **Custom entries** — any other CDN or office proxy, as IPs or CIDRs.
- **Real IP header** — defaults to `X-Forwarded-For`, exactly as before.

**Not needed for Cloudflare Tunnel** — a tunnel already delivers the real client address. This only affects proxy mode pointing at a publicly reachable NPG.

### ⚠️ Before changing the header

Selecting something like `CF-Connecting-IP` means **requests that do not carry it keep the proxy's address**. If anything else also sits in front of NPG (a router, HAProxy, a NAS, another nginx), that traffic is recorded with a private address and **a country whitelist can block all of it**. Change it only when Cloudflare is the only thing in front. The screen carries the same warning.

### Guard rails

Trusting too broadly lets visitors forge their own address, which defeats country restriction, access lists, banned IPs, fail2ban and rate limiting **at the same time**. The list is therefore capped by the **total number of addresses** it covers, and anything over answers with the reason. That rejects `0.0.0.0/0`, and also the workaround of listing 256 separate `/8` blocks to trust the whole internet.

Private and loopback ranges are **always trusted** and cannot be removed — Docker's own traffic and LAN proxies depend on them. If your internal proxy lives in one (`10.0.0.0/8` and friends), you can list it explicitly too: an internet client cannot send from those, so they do not count against the cap.

> **Leaving the setting alone changes nothing.** The generated nginx configuration is byte-identical to before.

> After enabling trusted proxies, **review your Banned IPs.** If you worked around this by adding Cloudflare edge addresses to trusted or banned lists, those entries no longer match anything.

> **Not to be confused with the similarly named setting** — this screen governs **proxied traffic** (GeoIP, access lists, banned IPs, fail2ban, rate limiting). The `TRUSTED_PROXY_CIDR` environment variable is separate and governs NPG's own admin panel: login lockout and API-token IP restrictions.

## 🔢 Type any status code in the log viewer

The status filter offered **17 fixed buttons**, so codes nginx actually logs — `499`, `444` — **could not be selected at all**.

Three ways to filter now:

- **By class** — `2xx`, `4xx` and so on, in one click
- **Common codes** — still one click
- **Free entry** — `499`, `444`, `4xx`, anything; comma-separated lists paste in fine

**Status codes can now be excluded too.** Exclusion covered IPs, user agents, URIs, hosts and countries; you can now hide `200` or all `3xx`.

Typos are reported when you apply them. Previously a bad value was silently ignored, leaving a view that looked filtered and was not.

> Error-log rows have no status code and stay visible when codes are excluded. Note that **WAF-blocked requests are 403**, so excluding 403 hides them too.

## 🚪 Direct IP blocking (444) now actually returns 444

With **Settings → Direct IP Access** set to "Close Connection (444)", some requests were still logged as **400**.

The biggest cause was **cleartext HTTP sent to the HTTPS port** — a browser or scanner speaking `http` to your `https` port. nginx finalizes that **before the content phase**, so the 444 rule never got a chance to run. It was **52% of a week's 400s** on one install.

Those now close the connection like everything else.

> **What deliberately did not change**
> - **A genuinely malformed request still answers 400.** When the request line is broken or the Host header is missing, nginx rejects it before reading the Host — so closing the connection there would silently drop malformed requests aimed at a hostname you **have** configured, leaving a client with a buggy HTTP library no way to diagnose it. These are mostly scanner noise and remain visible in the log
> - **"Return 403" is untouched.** Answering protocol garbage with the 10KB access-denied page makes the reply over 70x the request — a reflection surface not worth opening
> - **"Show welcome page" is untouched** — you asked for nothing to be blocked, so nginx's own behaviour stands

Also worth knowing: **direct IP access over HTTPS** is refused during the TLS handshake, so no HTTP status is ever recorded. Seeing nothing in the log is the expected outcome. The settings screen now says so.

> Thanks to **@re-birkin** for reading the logs closely. (#280)

## 🐞 Malformed requests were recorded incorrectly

When parsing the log line for a malformed request — a scanner's non-HTTP bytes, for instance — the request method came out as a stray value and **the host was lost**. About 161 rows a week.

The lost host is the part that matters: **fail2ban only counts a failure it can attribute to a host.** Both are now recorded correctly.

## 🔢 Exploit rule input is validated

Creating a rule with an unsupported `pattern_type` (where the pattern is applied) **saved successfully** — but the nginx configuration branches on that value, so the rule **appeared enabled in the list while blocking nothing**.

`severity` accepted any string too. Both are now rejected at save time with the accepted values named. The rule **update** path had no validation at all; it does now, including the regex.

The API specification was out of sync with the implementation and has been rewritten — a required field was missing, and fields that do not exist were documented.
