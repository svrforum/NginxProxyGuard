## 🚨 와일드카드 도메인을 쓰고 계셨다면 자동 차단이 꺼져 있었습니다

`*.example.com` 같은 **와일드카드 도메인**으로 프록시 호스트를 만드셨다면, 그 호스트의 **fail2ban과 WAF 자동 차단이 한 번도 동작하지 않았습니다.** 설정 화면에는 "활성"으로 보이는데도요.

원인은 이렇습니다. NPG는 접근 로그의 호스트명을 프록시 호스트에 연결한 뒤에야 실패를 셉니다. 그런데 이 연결이 **정확히 일치하는 도메인만** 찾고 있어서, `sub.example.com`으로 들어온 요청이 `*.example.com` 호스트와 맺어지지 못했습니다. 연결이 안 되면 실패로 세지도 않으므로, 임계값에 영원히 도달하지 않습니다.

이제 nginx와 같은 방식으로 맺어집니다 — 하위 도메인 깊이에 관계없이 매칭되고, 본체 도메인(`example.com`)은 포함하지 않으며, 더 구체적인 와일드카드가 우선합니다.

> ### ⚠️ 업그레이드 후 차단이 시작될 수 있습니다
>
> 와일드카드 호스트에 fail2ban이나 WAF 자동 차단을 켜 두셨다면, 지금까지 아무 일도 없었던 설정이 **업그레이드 직후부터 실제로 IP를 차단하기 시작합니다.** 임계값이 의도보다 낮게 잡혀 있지 않은지 한 번 확인해 주세요.

**새 호스트가 보호받기까지의 공백도 없앴습니다.** 이전에는 호스트를 만든 직후 최대 1분 동안 연결이 안 돼 무방비였습니다.

## 🔁 Valkey 사용 여부에 따라 차단 시점이 달랐습니다

"몇 초 안에 몇 번 실패하면 차단"에서 그 **"몇 초"가 Valkey를 쓸 때 제대로 지켜지지 않았습니다.**

실패가 들어올 때마다 시간 창이 뒤로 밀려서, **간격을 두고 조금씩 실패를 흘리는 IP는 창이 영영 끝나지 않고 누적**되다가 결국 차단됐습니다. Valkey 없이 쓰시는 경우에는 정상적으로 동작해서, **같은 설정인데 결과가 달랐습니다.**

이제 양쪽이 같게 동작합니다. 이미 WAF 자동 차단이 쓰고 있던 방식으로 통일했습니다.

> 업그레이드 후에는 **차단이 조금 줄어들 수 있습니다.** 원래 차단되지 말았어야 할 것이 차단되고 있었기 때문입니다.

## 🛡️ 자기 자신과 신뢰 프록시는 이제 차단하지 않습니다

두 종류의 주소는 어떤 경우에도 자동 차단하지 않습니다.

**루프백(`127.0.0.1`)** — 자기 자신을 차단하면 그 차단이 모든 호스트에 적용되는데, 이 검사는 nginx 처리 순서상 **인증서 갱신 경로보다 먼저** 실행됩니다. 즉 **모든 호스트의 인증서 자동 갱신이 멈춥니다.** 게다가 IP로 직접 접속하는 요청을 끊도록 설정하신 경우, 서버 안에서 도는 평범한 자체 점검만으로도 임계값에 도달할 수 있었습니다.

**설정 → 신뢰 프록시에 직접 넣으신 대역** — 프록시 주소 하나를 막으면 그 뒤에 있는 **모든 방문자**가 막힙니다.

> 사설망 주소(`192.168.x.x` 등)는 **그대로 차단할 수 있습니다.** 내부 기기를 의도적으로 막으실 수 있어야 하기 때문입니다.

차단하지 않기로 결정하면 그 이유를 로그에 한 줄 남깁니다. 기대한 차단이 일어나지 않았을 때 이유를 알 수 있어야 하기 때문입니다.

> **이미 차단 목록에 `127.0.0.1`이 들어가 있다면** 업그레이드가 자동으로 지우지는 않습니다. 차단 IP 목록에서 한 번 확인해 주세요.

## 🚨 Automatic banning was switched off on wildcard domains

If you have a proxy host on a **wildcard domain** such as `*.example.com`, that host's **fail2ban and WAF auto-ban never ran** — while the settings screen showed them enabled.

NPG counts a failure only after matching the access log's hostname to a proxy host, and that match looked for an **exact** domain. A request for `sub.example.com` therefore never matched the `*.example.com` host, was never counted, and no threshold was ever reached.

Matching now follows nginx's own rules: any depth of subdomain, never the bare domain itself, and the most specific wildcard wins.

> ### ⚠️ Expect bans to start after upgrading
>
> If fail2ban or WAF auto-ban is enabled on a wildcard host, a configuration that has been doing nothing **starts banning addresses immediately after the upgrade.** Worth checking the threshold is not lower than you intended.

**The gap for newly created hosts is closed too.** A host used to be unmatched — and therefore unprotected — for up to a minute after it was created.

---

## 🔁 Ban timing differed depending on whether you run Valkey

In "ban after N failures within M seconds", the **M was not being honoured when Valkey is in use.**

Every failure pushed the window forward, so an address trickling failures with gaps **accumulated indefinitely** instead of ageing out, and was eventually banned. Without Valkey the window behaved correctly — so the same configuration produced different results.

Both paths now behave identically, using the approach WAF auto-ban already used.

> You may see **slightly fewer bans** after upgrading. Some of what was being banned should not have been.

## 🛡️ NPG no longer bans itself, or your trusted proxies

Two kinds of address are never auto-banned.

**Loopback (`127.0.0.1`)** — a self-ban applies to every host, and that check runs earlier in nginx's processing than the certificate-challenge path, so it **stops automatic certificate renewal on every host**. With direct-IP requests set to be dropped, ordinary self-checks running inside the server could reach a threshold on their own.

**Anything inside the ranges you entered under Settings → Trusted Proxies** — banning one proxy address bans **every visitor behind it**.

> Private addresses (`192.168.x.x` and friends) **remain bannable**: you must still be able to block an internal device on purpose.

When a ban is refused, the reason is logged, so a ban you expected and did not get is explicable.

> **If `127.0.0.1` is already in your banned list**, upgrading does not remove it. Worth a look at the Banned IPs page.
