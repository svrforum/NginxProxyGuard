## ✨ New: sign in with Google, Authentik, Authelia or any OpenID Connect provider

You can now sign in to the NPG admin panel with an external identity provider instead of, or alongside, a password. (#227)

**Settings → SSO** walks you through it in three steps: pick your provider, connect it, then say who may sign in. Picking a provider fills in the parts nobody remembers — Google's fixed issuer URL, Authentik's application slug, Keycloak's realm — and shows the setup steps to follow **at your provider**, with the exact callback URL to paste right in the instruction.

- **The callback URL is shown before you save.** Google and Authentik both want the redirect URI while you are still creating the client, so it is available from the moment you name the provider.
- **Test connection** fetches the provider's discovery document and tells you the issuer it answered with, whether PKCE is supported, and any scope it does not advertise — before a single person tries to sign in.
- **Password sign-in always stays available.** NPG is often the reverse proxy in front of the very provider you are configuring, so an SSO-only panel would lock you out of the tool you need to fix it. There is deliberately no way to turn it off.

**A note on Google specifically.** It works, but it is the weakest of the four. Google sends no group information over OIDC, so roles are assigned per account here rather than centrally, and it refuses any callback URL that is not https on a real domain — no IP addresses. If the panel is reached at `http://192.168.x.y`, Google cannot be used at all, and the form now says so the moment you pick it instead of after you have registered a client. Where Google shines is a Google Workspace organisation with the app's Audience set to Internal, where the organisation boundary does real work.

### Who gets an account, and with what role

Signing in successfully is not the same as being allowed in — a provider like Google authenticates every account on earth. So automatic account creation stays off until you say who qualifies: an allowed email domain, specific addresses, or membership of a group. Leave all three empty and NPG refuses to create anything.

- New accounts receive the role you choose.
- Add **group → role mappings** and the role is recomputed at every sign-in, so revoking a group at your provider takes effect on the next login. Without mappings, NPG owns the role after the account is created.
- If you set a group rule without requesting the `groups` scope, the form now warns you and offers to add it — otherwise every sign-in would be refused with no explanation.
- An existing NPG account is **linked**, not duplicated, when the provider reports a matching verified email. Your own account keeps its history and gains SSO.

**Settings → Users** shows which identity providers each account can sign in through, so a federated account is distinguishable from a local one.

## 🔒 Security notes

- Configuring an identity provider requires the **user administration** permission, not settings. A provider decides who may hold an account here and with what role, which is the same power as assigning a role directly.
- The sign-in request is bound to the browser that started it, so a callback URL captured by someone else cannot sign your browser in as them.
- The client secret is never returned by the API once stored, and the session token is handed to the browser in the URL fragment, which never reaches a server log.

## 🩹 Fixes

- The admin UI proxy now forwards the port along with the host. On a panel reached on a non-standard port (`:81`, for example) the API previously built OIDC redirect URIs without it, so the value registered at the provider and the value NPG sent did not match.
