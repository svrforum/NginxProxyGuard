## 🛡️ 대용량 업로드 설정이 WAF를 통째로 끄고 있었습니다

### ⚠️ 이 설정을 쓰고 계셨다면 지금까지 요청 검사가 없었습니다

**성능 → 프록시 요청 버퍼링을 off로 두셨다면**, 그 호스트의 WAF는 요청을 하나도 검사하지 않고 있었습니다. 전역 설정으로 off를 두신 경우에는 **모든 호스트**가 해당됩니다.

이유는 이렇습니다. 그동안 NPG는 요청 버퍼링이 꺼진 WAF 호스트에 `SecRequestBodyAccess Off`를 자동으로 넣었습니다. 주석에는 "본문 검사만 끄고 헤더와 URL 패턴은 계속 보호한다"고 적혀 있었는데, **사실이 아니었습니다.** ModSecurity v3는 이 설정이 꺼지면 phase 2 전체를 건너뜁니다. 그런데 OWASP CRS는 점수 누적 방식이라 **차단 판정 자체가 phase 2**에 있습니다. 결과적으로 헤더도 URL도 아무것도 막지 못했습니다.

실제로 측정해 봤습니다. 차단 모드 호스트에서 이 설정을 켠 전후로 같은 요청을 보냈더니:

| 공격 | 설정 전 | 설정 후 |
|---|---|---|
| 쿼리스트링 SQL 인젝션 | 403 | **200** |
| 쿼리스트링 XSS | 403 | **200** |
| 경로 탐색 (`../../etc/passwd`) | 403 | **200** |
| 스캐너 User-Agent | 403 | **200** |
| log4shell 헤더 | 403 | **200** |
| 본문 SQL 인젝션 · RCE | 403 | **200** |

10건 중 10건이 통과했습니다. 더 나쁜 건 **화면상으로는 WAF가 살아 있어 보였다**는 점입니다. 스캐너 탐지 같은 일부 규칙은 계속 발화해서 WAF 이벤트 목록에 기록이 쌓이는데, 응답은 200이었습니다.

**그리고 이 설정은 아무 이득도 없었습니다.** 300MB 업로드로 확인해 보니, 이 설정이 있든 없든 임시 파일이 **똑같이 314MB까지** 자랐습니다. WAF가 켜진 호스트에서는 ModSecurity 커넥터가 본문 전체를 어차피 읽기 때문에, 어떤 설정으로도 스트리밍이 되지 않습니다.

**이제 이 설정을 넣지 않습니다.** 업그레이드하면 요청 검사가 곧바로 복원됩니다.

## 📎 파일 업로드가 WAF에 막히던 문제

정상적인 파일 업로드가 403으로 거부되는 일이 있었습니다. ModSecurity v3의 멀티파트 파서가 **규격에 맞는 본문에도** "경계 문자열이 맞지 않음" 플래그를 세우고, 그 플래그가 곧바로 차단으로 이어졌기 때문입니다.

위의 `SecRequestBodyAccess Off`는 사실 이 오탐을 덮고 있었습니다. 그런데 **오탐은 버퍼링 설정과 아무 상관이 없습니다** — 버퍼링을 켠 호스트도 똑같이 막혔습니다. 그래서 정작 업로드가 깨진 호스트들은 아무 완화도 받지 못한 채, 엉뚱한 호스트의 WAF만 꺼져 있었습니다.

이제 WAF를 켠 모든 호스트에서 **파서의 오탐 규칙 두 개만** 제거합니다. CRS의 멀티파트 우회 탐지와 본문에 대한 모든 검사는 그대로 동작합니다.

> 본문을 **아예 파싱할 수 없는** 요청(깨진 JSON·XML 포함)에 대한 차단은 그대로 둡니다. 파싱이 안 된 본문은 검사할 대상이 없으므로, 그 차단이 유일한 방어선입니다.

## 🔢 WAF가 POST를 차단하면 405를 돌려주던 문제

본문이 있는 요청을 WAF가 막으면 클라이언트는 **403이 아니라 405 Not Allowed**를 받았습니다. 차단 안내 페이지를 정적 파일로 서빙하는 과정에서 nginx가 POST에 405로 답하기 때문이었습니다.

로그에도 405로 기록됐습니다. 그래서 **fail2ban의 실패 코드를 403으로 두셨다면 본문 공격 차단은 하나도 세어지지 않았고**, 403을 세는 대시보드 숫자에서도 빠져 있었습니다. 이제 403을 돌려주고 403으로 기록합니다.

## 🌍 지오 챌린지 모드에서 WAF가 검사를 못 하던 문제

국가 차단을 **챌린지 모드**로 쓰는 호스트에서, WAF가 요청을 제대로 검사하지 못했습니다.

챌린지 대상 요청은 CAPTCHA 페이지로 리다이렉트되는데, 이 리다이렉트가 nginx의 이른 처리 단계에서 요청을 끝내 버려 **ModSecurity의 차단 판정 단계가 실행되지 않았습니다.** 개발 환경 로그로 확인해 보니 명확했습니다 — 챌린지로 끝난 요청 중 SQL 인젝션 탐지(942100)는 **0건**, 같은 호스트의 일반 차단 요청에서는 2,565건이었습니다. 스캐너 탐지 같은 앞단 규칙만 로그에 남고, 실제 공격은 **로그조차 남지 않았습니다.**

이제 챌린지 판단을 뒤쪽 단계로 옮겨서, **WAF가 먼저 검사한 뒤** 챌린지가 결정됩니다. 해외 방문자 경험은 그대로입니다(쿠키 없으면 CAPTCHA, 유효한 쿠키면 통과, 검색봇은 예외). 추가 API 호출도 없고, API가 내려가 있을 때의 동작도 이전과 같습니다.

## 🚫 fail2ban "알림만"이 실제로는 차단하던 문제

액션을 **"알림만"** 으로 두셨어도 IP가 **실제로 차단**됐습니다. 화면의 약속과 정반대였습니다.

이제 세 가지가 이름대로 동작합니다.

| 액션 | 동작 |
|---|---|
| **IP 차단** | 차단 + 알림 |
| **알림만** | 차단하지 않고 알림만 |
| **로그만 기록** | 컨테이너 로그에만 기록 |

"알림만"을 위한 알림 이벤트(**IP 감지 — 차단 안 함**)를 새로 추가했습니다. 알림 설정에서 따로 켜실 수 있습니다.

## ✅ fail2ban 실패 코드 입력 검증

실패 코드에 `4o1`(숫자 0이 아닌 알파벳 o), `401;403`(쉼표 대신 세미콜론), `4xx` 같은 값을 넣어도 **저장은 정상적으로 됐고, 그다음 영원히 아무것도 매칭되지 않았습니다.** 왜 안 걸리는지 알 방법이 없었습니다. 이제 저장할 때 거절하고 무엇이 잘못됐는지 알려 드립니다.

**실패 코드에 대해 한 가지 알아 두실 점이 있습니다.** fail2ban은 **그 호스트가 직접 응답한 코드만** 셉니다. IP로 직접 접속해 온 요청을 끊는 `444`는 어느 프록시 호스트에도 속하지 않기 때문에, 실패 코드에 넣으셔도 발동하지 않습니다. 도움말에도 이 내용을 적어 두었습니다. (#271)

## 🛡️ A large-upload setting was disabling the WAF entirely

### ⚠️ If you used it, requests were not being inspected at all

**If you set Performance → Proxy Request Buffering to off**, that host's WAF was inspecting nothing. If you set it globally, that applied to **every** host.

Here is what was happening. NPG emitted `SecRequestBodyAccess Off` on WAF-enabled hosts whose request buffering was off. The comment claimed it only disabled body inspection and that "WAF still protects headers, URL patterns". That was **not true**. ModSecurity v3 skips all of phase 2 when that directive is off — and because OWASP CRS runs in anomaly-scoring mode, **the blocking decision itself lives in phase 2**. Nothing was blocked.

Measured on a blocking-mode host, identical requests before and after the directive:

| Attack | Without | With |
|---|---|---|
| SQL injection in query string | 403 | **200** |
| XSS in query string | 403 | **200** |
| Path traversal (`../../etc/passwd`) | 403 | **200** |
| Scanner User-Agent | 403 | **200** |
| log4shell header | 403 | **200** |
| SQL injection / RCE in body | 403 | **200** |

Ten out of ten got through. Worse, **the WAF still looked alive**: some phase-1 rules kept firing, so events kept arriving in the WAF log — with a 200 response.

**And the directive bought nothing.** Sampling a 300MB upload showed the temp file growing to **the same 314MB** with or without it. On a WAF-enabled host the ModSecurity connector reads the whole body regardless, so no configuration can stream around it.

**The directive is no longer emitted.** Upgrading restores request inspection immediately.

## 📎 File uploads blocked by the WAF

Ordinary file uploads were rejected with 403. ModSecurity v3's multipart parser raises an "unmatched boundary" flag on **spec-compliant** bodies, and that flag denied the request outright.

The directive above was in fact papering over this. But **the false positive has nothing to do with buffering** — hosts with buffering left on were hit just as hard. So the hosts whose uploads were actually broken got no mitigation, while unrelated hosts had their WAF switched off.

Now every WAF-enabled host drops **just the two parser false-positive rules**. CRS multipart-evasion detection and all body inspection continue to run.

> The deny for bodies that cannot be parsed **at all** (malformed JSON and XML included) is deliberately kept. A body that failed to parse populates nothing for the rules to inspect, so that deny is the only thing left.

## 🔢 WAF blocks on POST answered 405

When the WAF blocked a request with a body, the client got **405 Not Allowed, not 403** — nginx answers a POST that way when the block page is served as a static file.

It was logged as 405 too. So **if your fail2ban fail codes included 403, body attacks never counted**, and they were missing from any 403-based dashboard figure. It now answers and logs 403.

## 🌍 The WAF could not inspect challenged requests

On hosts using **challenge mode** for country restriction, the WAF was not properly inspecting requests.

A challenged request is redirected to the CAPTCHA page, and that redirect ended the request early enough that **ModSecurity's blocking stage never ran**. The logs made it unambiguous: among requests that ended in a challenge, SQL-injection detections (942100) numbered **zero**, versus 2,565 on ordinary blocked requests for the same host. Only early-stage rules such as scanner detection were logged; real attacks **were not logged at all**.

The challenge decision now happens later, so **the WAF inspects first**. The visitor experience is unchanged (no cookie → CAPTCHA, valid cookie → through, search bots exempt), with no extra API calls and no change to behavior while the API is down.

## 🚫 fail2ban "Notify Only" was banning

With the action set to **Notify Only**, the address was **actually banned** — the opposite of what the control promised.

The three actions now do what they say:

| Action | Behavior |
|---|---|
| **Block IP** | Bans and notifies |
| **Notify Only** | Notifies without banning |
| **Log Only** | Container log only |

A notification event for it (**IP detected — not banned**) is now available in the alert settings.

## ✅ fail2ban fail codes are validated

Values like `4o1`, `401;403` or `4xx` **saved successfully and then silently never matched**, with no way to tell why. They are now rejected at save time with the reason.

**One thing worth knowing about fail codes:** fail2ban only counts responses **the host itself answered**. `444`, which drops requests that arrived by IP with no matching host, belongs to no proxy host — adding it to the fail codes cannot fire. The help text now says so. (#271)
