## 🔒 보안

### 로그인 IP를 위조할 수 있던 문제

NPG가 기록하던 접속 IP는 **요청자가 직접 써 보낼 수 있는 값**이었습니다. `X-Forwarded-For` 헤더를 무조건 믿고 맨 앞 값을 그대로 사용했기 때문입니다.

화면에 잘못된 IP가 보이는 것으로 끝나지 않습니다. **로그인 실패 잠금이 IP별로 집계**되기 때문에, 헤더 값만 바꿔 가며 시도하면 한 주소에 실패가 쌓이지 않아 **5회 잠금이 영영 걸리지 않습니다.** 헤더 한 줄로 무차별 대입 방어가 무력화됐습니다.

이제 헤더를 **오른쪽부터 거슬러 읽어**, 저희가 거친 구간(내부망·루프백)을 건너뛰고 **저희가 붙이지 않은 첫 주소**를 씁니다. nginx는 구간마다 실제 상대방 주소를 뒤에 덧붙이므로 그것이 진짜 클라이언트이고, 클라이언트가 임의로 써넣은 값은 그보다 왼쪽에 남아 읽히지 않습니다.

검증은 nginx가 인터넷 클라이언트에게 실제로 만들어 주는 형태(`위조값, 실제주소, 프록시주소`)로 했습니다. 수정 전에는 위조값이 기록됐고, 지금은 실제 주소가 기록됩니다.

**남는 한계**도 적어 둡니다. 이미 **사설망 안에 있는** 요청자는 그 구간 자체가 신뢰 대상이라 건너뛰어지므로 여전히 값을 지정할 수 있습니다. 이를 막으려면 NPG 자신의 프록시가 올라가 있는 도커 네트워크를 불신해야 해서, 지금은 이 선을 택했습니다.

**대시보드의 마지막 로그인 IP가 내부 주소로 보이던 것도** 같은 원인이라 함께 해결됩니다.

> 신고해 주신 **@heygoodluck** 님 감사합니다. (#254)

## 🩹 수정

### 인증서 다운로드가 안 될 때 이유를 알려줍니다

"Certificate data not available" 는 증상만 말하고 무엇을 해야 하는지는 알려주지 않았습니다.

이 메시지는 인증서가 **발급됨으로 표시돼 있는데 실제 인증서 데이터가 저장돼 있지 않을 때** 나옵니다. 이제 **무엇이 없는지**(인증서인지 개인키인지)와 **어떻게 복구하는지**를 알려주며, 복구 방법은 종류에 따라 다릅니다.

- Let's Encrypt 등 자동 발급: **갱신**하면 다시 받아옵니다
- 직접 올린 인증서: **다시 업로드**하면 됩니다

아직 발급 중인 경우에도 현재 상태를 그대로 알려주므로, 기다리면 되는지 로그를 봐야 하는지 구분됩니다.

> 신고해 주신 **@heygoodluck** 님 감사합니다. (#253)

### 시놀로지에서 컨테이너 로그가 안 보이던 이유

신고자께서 직접 찾아 주셨습니다. 저희가 배포하는 `docker-compose.yml`이 모든 서비스에 로그 드라이버를 **명시**하는데, 시놀로지 DSM의 컨테이너 관리자는 자체 로그 저장소를 읽기 때문에 드라이버를 지정한 컨테이너는 화면에 아무것도 안 나옵니다.

저희가 그걸 지정한 이유는 **로그가 디스크를 채우는 사고**를 막기 위해서입니다(홈서버에서 실제로 자주 터지는 문제입니다). 그래서 지우지 않고, **compose 파일에 이유와 대처를 함께 적었습니다.** DSM 화면에서 로그를 보고 싶으시면 해당 블록을 주석 처리하시면 되고, `docker logs` 는 어느 쪽이든 정상 동작합니다.

## 🔒 Security

### The recorded sign-in IP address could be forged

The address NPG recorded was a value the caller could write. `X-Forwarded-For` was trusted unconditionally and its leftmost entry used as-is.

That is worse than a wrong number on screen. **Failed sign-ins are counted per IP address**, so anyone varying the header never accumulated failures against a single address, and **the five-attempt lockout never fired** — brute-force protection was defeated by adding a header.

The header is now read **from the right**, skipping the hops we run (private networks and loopback), taking the **first address we did not add ourselves**. nginx appends the actual peer at each hop, so that entry is the real client; anything the client wrote sits further left and is never reached.

Verified with the chain nginx builds for an internet client (`forged, client, proxy`): before the change the forged value was stored, now the client address is.

**A limit worth stating.** A caller already **on a private network** is itself a trusted hop, so its entry is skipped and it can still supply the value. Closing that would mean refusing to trust the Docker network NPG's own proxy runs on, so the line is drawn here.

This also fixes **the last-login address showing an internal IP** on the dashboard — same cause.

> Thanks to **@heygoodluck** for the report. (#254)

## 🩹 Fixes

### Certificate downloads now say why there is nothing to download

"Certificate data not available" named the symptom and gave the operator nowhere to go.

It appears when a certificate is marked **issued** but the material was never stored. The message now says **what is missing** — the certificate, the key, or both — and **what recovers it**, which depends on the kind:

- Issued automatically (Let's Encrypt and similar): **renew** it to fetch the material again
- Uploaded by hand: **upload** the certificate and key again

If issuance simply has not finished, the message names the actual status, so you can tell waiting from investigating.

> Thanks to **@heygoodluck** for the report. (#253)

### Why Synology showed no container logs

The reporter found this one themselves. Our published `docker-compose.yml` pins a log driver on every service, and Synology DSM's Container Manager reads its own log store — so a container that pins a driver shows nothing in its viewer.

The pin exists to **cap log size**, the failure that actually bites a home server. Rather than remove it, the compose file now explains the trade-off where you will find it: comment the block out if you want logs in DSM's viewer. `docker logs` works either way.

> Thanks to **@re-birkin** for tracing it. (#251)
