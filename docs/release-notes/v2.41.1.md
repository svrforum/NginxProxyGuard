## 🩹 수정

### 컨테이너 시작 때마다 뜨던 마이그레이션 에러

일부 환경에서 부팅할 때마다 아래 에러가 나고, "스키마가 부분적으로만 반영됐을 수 있다"는 경고가 함께 떴습니다.

```
[Migration] ERROR: 1 upgrade statement(s) failed …
Detach orphan chunk inheritance entries (TimescaleDB catalog drift):
pq: column ch.schema_name does not exist (42703)
```

원인은 저희가 TimescaleDB의 **내부 카탈로그**를 직접 읽고 있었기 때문입니다. 그 내부 구조는 공개 API가 아니라 버전에 따라 바뀌고, 저희보다 새로운 TimescaleDB를 쓰시는 분들에게서 컬럼이 사라졌습니다.

이제 **공식 문서에 정의된 뷰**(`timescaledb_information`)를 통해 읽습니다. 그리고 이 정리 작업은 예전 버전이 남긴 흔적을 치우는 것일 뿐 다른 기능이 의존하지 않으므로, 앞으로 비슷한 변화가 또 있어도 **에러 대신 안내 문구**로 넘어갑니다.

PostgreSQL 17·18 어느 쪽이든 영향받으셨다면 이번 업데이트로 사라집니다.

### 대시보드 평균 응답시간이 실제보다 크게 나오던 문제

평균 응답시간이 실제 체감보다 훨씬 크게(때로 만 단위로) 나오는 경우가 있었습니다.

시간별 통계의 **평균을 다시 평균 내고 있었던 것**이 원인입니다. 요청이 2건뿐인 시간과 10만 건인 시간이 똑같은 비중으로 계산돼서, 한산한 시간대에 느린 요청 하나만 들어와도 24시간 평균 전체가 끌려 올라갔습니다.

이제 **요청 수로 가중치를 두어** 계산합니다. 실제 데이터로 비교하면 같은 구간이 136.43ms → **121.46ms** 로, 체감에 맞는 값이 나옵니다.

일별 통계도 같은 방식으로 고쳤습니다. 이쪽은 값이 **저장되기 때문에** 한 번 잘못 계산되면 그 날짜가 계속 틀린 채로 남아 더 중요했습니다.

## 🩹 Fixes

### A migration error on every container start

On some installs, every boot printed this, together with a warning that the schema might be only partially migrated:

```
[Migration] ERROR: 1 upgrade statement(s) failed …
Detach orphan chunk inheritance entries (TimescaleDB catalog drift):
pq: column ch.schema_name does not exist (42703)
```

The cause was ours: the statement read TimescaleDB's **private catalog** directly. That catalog's shape is not part of TimescaleDB's API and does change between releases — the column had gone on newer builds than the one we ship.

It now reads the **documented views** (`timescaledb_information`) instead. And because this step only tidies leftovers from older TimescaleDB versions, with nothing downstream depending on it, a future change degrades to a notice rather than an error.

If you were affected on PostgreSQL 17 or 18, this update clears it.

### The dashboard's average response time read far too high

Average response time could come out much larger than anything you would actually experience — sometimes in the tens of thousands.

It was **averaging hourly averages**. An hour holding two requests counted exactly as much as an hour holding a hundred thousand, so one slow request in a quiet hour dragged the whole 24-hour figure up with it.

It is now **weighted by request count**. On real data the same window reads 136.43ms unweighted against **121.46ms** weighted — the figure that matches what you see.

The daily rollup had the same flaw and is fixed too. That one mattered more because the value is **stored**: once written wrong, that day stayed wrong.
