## 🔴 인증서 — 지금 바로 확인해 주세요

### 갱신 버튼이 인증서 개인키를 지우고 있었습니다

SSL 인증서 화면에서 **갱신(Renew)** 을 누르면, NPG가 데이터베이스에 보관하던 **인증서·개인키·발급자 체인·Let's Encrypt 계정 정보를 전부 비워 버렸습니다.** 갱신이 성공하면 새 값으로 다시 채워졌지만, **실패하면 상태만 "발급됨"으로 되돌려 놓고 내용은 빈 채로 남았습니다.**

겉으로는 아무 일도 없어 보입니다. nginx는 인증서를 데이터베이스가 아니라 **디스크의 파일**에서 읽기 때문에, HTTPS는 그대로 동작하고 `nginx -t`도 통과합니다. 문제는 다운로드하거나, 백업을 다른 서버에 복구하거나, 갱신이 필요해진 시점에 드러납니다.

같은 이유로 **"인증서 생성 후 즉시 다운로드가 안 된다"** 는 증상(#253)도 발생했습니다. 발급 직후에는 캐시에 개인키가 빠진 사본이 남아 있어서 다운로드가 거부됐고, 1분쯤 지나 캐시가 만료되면 다시 됐습니다.

**직접 업로드한 인증서는 더 심각했습니다.** `새 인증서 → 업로드`로 등록한 인증서는 **v1.0.1 이래 한 번도 키 내용이 저장된 적이 없습니다.** 파일은 디스크에 정상적으로 저장됐지만 데이터베이스 쪽은 항상 비어 있었습니다.

**v2.45.0에서 이렇게 바뀝니다.**

- 상태만 바꾸는 저장과 키 내용을 쓰는 저장을 분리했습니다. 어떤 경로로도 기존 키를 실수로 지울 수 없습니다.
- 개인키를 담을 수 없는 캐시를 제거했습니다. 발급 직후 다운로드가 바로 됩니다.
- 업로드한 인증서의 키가 정상적으로 저장됩니다.
- **이미 비어 버린 행은 자동으로 복구됩니다.** 다운로드를 시도하면 디스크의 `fullchain.pem`·`privkey.pem`을 다시 읽어 데이터베이스를 채운 뒤 파일을 내려 줍니다.

**업그레이드 전에 갱신 버튼을 누르지 마세요.** v2.13.18 ~ v2.44.0을 쓰고 계신다면, 지금 누르는 갱신이 남아 있는 키를 지웁니다. 먼저 업그레이드하시면 됩니다.

**업그레이드 후 확인하실 것 두 가지입니다.**

1. 인증서 목록에서 각 인증서를 한 번씩 **다운로드**해 보세요. 자동 발급 인증서는 대부분 이 과정에서 조용히 복구됩니다.
2. 그래도 *"파일로도 복구할 수 없습니다"* 라는 안내가 나오는 인증서는 디스크 파일까지 없는 경우입니다. 자동 발급이면 **갱신**(이제 안전합니다), 직접 올리신 인증서면 해당 인증서를 열어 **수정(Update)** 에서 다시 업로드해 주세요. **새 인증서 추가는 별도 항목을 만들 뿐 이 인증서를 고치지 못합니다.**

이 기간에 받아 두신 **백업에는 키가 비어 있을 수 있습니다.** 다른 서버에 복구할 계획이 있으시면, 업그레이드하고 위 절차로 복구한 뒤 백업을 다시 받으시길 권합니다.

> 참고: 키가 비면 Let's Encrypt 계정 정보도 함께 비워졌기 때문에, 갱신할 때마다 **계정을 새로 등록**했습니다. Let's Encrypt는 IP당 3시간에 10개로 신규 등록을 제한하므로, 갱신을 반복하다 발급 자체가 막힐 수 있었습니다. 이제 계정 정보는 별도로 보관되어 재사용됩니다.

> 제보해 주신 **@heygoodluck** 님 감사합니다. (#253)

## 🗄️ 백업 복구

### 직접 만든 차단 규칙이 있으면 복구가 통째로 실패했습니다

**Exploit 차단 규칙을 하나라도 직접 만드셨다면, 그 백업은 복구되지 않았습니다.** 복구가 HTTP 500과 함께 데이터베이스 오류를 내고 전체가 롤백됐습니다. 내장 규칙만 있는 백업은 정상이었기 때문에, 쓰는 사람에 따라 되기도 하고 안 되기도 했습니다.

원인은 존재하지 않는 제약 조건을 참조하는 저장 구문이었습니다. 설치 시점이나 업그레이드 여부와 무관하게 **처음부터 한 번도 동작한 적이 없던 경로**입니다. 이제 정상적으로 복구되며, 같은 이름의 규칙이 여러 개 있어도 그대로 살아납니다.

덤으로, **최신 버전에서 받은 백업을 구 버전에 복구할 때** 대상 설치에 없는 내장 규칙이 들어 있으면 역시 복구 전체가 실패했습니다. 이제 그런 규칙과 그에 딸린 예외만 건너뛰고 나머지는 복구됩니다.

> 제보해 주신 **@four2mis** 님 감사합니다. (#259)

### 복구가 nginx 기본 인증서를 0바이트로 만들던 문제

백업에 인증서가 포함돼 있으면, 복구가 **nginx의 기본 자체서명 인증서를 빈 파일로 만들어** 프록시 전체의 설정 검사(`nginx -t`)를 실패시켰습니다. 그 상태에서는 설정을 다시 불러올 수 없어, 이후의 모든 변경이 반영되지 않았습니다.

파일을 먼저 비우고 나서 권한을 설정하는 순서였는데, 그 권한 설정이 실패하면 비운 상태로 끝나 버렸습니다. API 컨테이너는 보안상 최소 권한으로 동작하기 때문에, nginx 컨테이너가 만든 파일에 대해서는 이 권한 설정이 **항상** 실패합니다.

이제 복구는 임시 파일에 먼저 기록한 뒤 통째로 교체합니다. **어떤 오류가 나더라도 기존 파일은 손상되지 않습니다.** 개인키를 다른 사용자가 읽지 못하게 하는 보호는 그대로이며, 오히려 내용이 기록되기 전에 적용됩니다.

**이미 이 문제를 겪으신 경우** — 설정 변경이 반영되지 않거나 `nginx -t`가 인증서를 못 읽는다고 한다면 — 프록시 컨테이너를 한 번 재시작하면 기본 인증서가 다시 만들어집니다.

```bash
docker compose restart nginx
```

## 🚫 IP 차단 기간 — Fail2ban 화면까지

지난 버전에서 차단 기간 목록을 하나로 통일하면서 **Fail2ban 설정 화면이 빠져 있었습니다.** 정작 처음 말씀해 주신 화면이 그쪽이었는데 놓쳤습니다.

이제 Fail2ban 차단 기간도 **5분부터 30일까지, 그리고 영구 차단**을 목록에서 고르실 수 있습니다.

- **영구 차단이 목록에 있습니다.** 예전에는 초 단위 입력칸에 `0`을 넣어야 했고, 그 사실이 화면 어디에도 없었습니다. 이제 한글·영어 설명 모두에 *"영구 차단(0초)은 만료되지 않습니다"* 라고 적혀 있습니다.
- **30일을 지정할 수 있습니다.** 예전 입력칸은 604800초(7일)가 상한이라 30일을 아예 표현할 수 없었습니다.
- 정확한 초를 원하시면 **직접 입력(초)** 을 고르시면 됩니다. 목록에 없는 값이 저장돼 있으면 그 칸이 열린 채로 표시됩니다.

이번에 함께 고친 것: **첫 저장에서 영구 차단이 저장되지 않던 버그.** 해당 호스트에 Fail2ban 설정이 아직 없는 상태에서 영구 차단을 고르면 조용히 1시간으로 바뀌어 저장됐습니다.

> 제보해 주신 **@re-birkin** 님 감사합니다. (#252)

> 참고: 이미 걸려 있는 차단의 기간을 **줄이는** 경우, 줄어든 만료 시각이 nginx에 즉시 반영되지는 않습니다. 늘리는 경우와 새로 차단하는 경우는 즉시 반영됩니다.

## 🔁 리다이렉트 설정이 시작 시 적용되지 않던 문제

API와 nginx를 **별도 컨테이너로 운영하는 구성**에서, API만 업그레이드·재시작하면 리다이렉트 호스트 설정이 디스크에서는 정리되는데 **이미 떠 있는 nginx는 예전 설정을 계속 서빙**할 수 있었습니다. nginx는 설정을 시작하거나 다시 불러올 때 메모리로 읽기 때문에, 파일만 지우는 것으로는 동작이 바뀌지 않습니다.

시작 순서도 함께 정리해서, 기본 서버 설정(직접 IP 접근 처리 등)도 확실하게 적용됩니다. 예전에는 nginx가 설정을 읽는 시점과 겹치는 운에 기대고 있었습니다.

## 🔴 Certificates — please read this one

### The Renew button was erasing your certificate's private key

Pressing **Renew** on an SSL certificate made NPG blank the **certificate, private key, issuer chain and Let's Encrypt account** it keeps in the database. A successful renewal refilled them — but **a failed one put the status back to "issued" and left the contents empty.**

Nothing looks wrong when this happens. nginx serves TLS from the **files on disk**, not from the database, so HTTPS keeps working and `nginx -t` still passes. You find out when you download the certificate, restore a backup onto another server, or need to renew.

The same cause produced the reported **"can't download a certificate right after creating it"** symptom (#253). Just after issuance a cached copy without the key material was being returned, so the download was refused; about a minute later the cache expired and it worked again.

**Uploaded certificates were worse.** A certificate added through **New certificate → Upload** has **never had its key material stored, since v1.0.1.** The files were written to disk correctly, but the database side was always empty.

**What changes in v2.45.0**

- Writes that only change status are now separate from writes that store key material, so no path can wipe an existing key.
- The cache that could not carry a private key is gone, so downloading right after issuance works.
- Uploaded certificates store their key material.
- **Rows that are already empty repair themselves.** Ask for a download and NPG reads `fullchain.pem` and `privkey.pem` back from disk, refills the row and serves the file.

**Do not press Renew before upgrading.** On v2.13.18 – v2.44.0 that press erases whatever key material is left. Upgrade first.

**After upgrading, two things are worth doing**

1. **Download** each certificate once from the list. Most automatically-issued certificates quietly repair themselves in the process.
2. If a certificate still says *its files could not restore it*, the files on disk are gone too. For an automatically-issued certificate, press **Renew** (safe now). For one you uploaded, open it and use **Update** to upload the certificate and key again — **adding a new certificate only creates a separate entry and does not fix this one.**

**Backups taken during this period may contain empty key material.** If you plan to restore onto another server, upgrade, repair as above, and take a fresh backup.

> Note: because the Let's Encrypt account was blanked along with the key, every renewal attempt **registered a brand new account**. Let's Encrypt caps new registrations at 10 per IP per 3 hours, so repeated attempts could block issuance entirely. The account is now stored separately and reused.

> Thanks to **@heygoodluck** for the report. (#253)

## 🗄️ Backup restore

### Restore failed completely if you had created your own block rules

**If you ever created an exploit block rule of your own, that backup would not restore.** The restore returned HTTP 500 with a database error and rolled the whole thing back. Backups containing only built-in rules restored fine, which is why some people hit this and others never did.

The cause was a statement referring to a constraint that does not exist — a path that **has never worked**, regardless of install age or upgrade history. Restore now completes, and rules that share a name are all preserved.

Related: **restoring a backup taken on a newer version onto an older install** also failed outright when it contained a built-in rule the target did not have. Those rules and their exclusions are now skipped and the rest is restored.

> Thanks to **@four2mis** for the report. (#259)

### Restore was emptying the nginx default certificate

When a backup contained certificates, restoring it **truncated nginx's default self-signed certificate to an empty file**, which made the whole proxy fail its configuration test (`nginx -t`). While in that state nginx cannot reload, so no later change took effect.

The code emptied the destination file first and then set its permissions — and when that permission step failed, it stopped there, leaving the file empty. The API container runs with minimal privileges by design, so that step **always** fails for files created by the nginx container.

Restore now writes to a temporary file and swaps it into place. **No failure can damage the existing file.** The protection that keeps restored private keys unreadable by others is unchanged, and is now applied before any content is written.

**If this already happened to you** — configuration changes not taking effect, or `nginx -t` complaining it cannot load the certificate — restart the proxy container once and the default certificate is regenerated:

```bash
docker compose restart nginx
```

## 🚫 Ban durations — now on the Fail2ban screen too

The previous release unified the ban-duration list but **missed the Fail2ban settings screen** — which was the screen originally reported.

Fail2ban ban duration is now chosen from the same list: **5 minutes through 30 days, plus permanent.**

- **Permanent is in the list.** It used to require typing `0` into a seconds box, and nothing on screen said so. Both the Korean and English help text now state that a permanent ban (0 seconds) never expires.
- **30 days can be selected.** The old box capped out at 604800 seconds (7 days), so 30 days could not be expressed at all.
- Choose **Custom (seconds)** for an exact number. A stored value that is not one of the offered durations opens on that field.

Fixed along the way: **permanent was not saved on the first save.** Choosing permanent for a host that had no Fail2ban configuration yet silently stored one hour instead.

> Thanks to **@re-birkin** for the report. (#252)

> Note: **shortening** an existing ban does not push the earlier expiry to nginx immediately. Extending a ban and adding a new one both apply immediately.

## 🔁 Redirect configuration was not applied at startup

In deployments where **API and nginx are separate containers**, upgrading and restarting only the API cleaned up redirect host configuration on disk while **an already-running nginx kept serving the old configuration**. nginx reads configuration into memory when it starts or reloads, so deleting files alone changes nothing.

Startup now regenerates redirect configuration and then runs `nginx -t` and applies it within the same lock. If the test fails it does not apply, and it says why.

Startup ordering was tidied at the same time, so the default server configuration (direct-IP handling and similar) is reliably applied too — previously it depended on happening to land before nginx read its configuration.

> Thanks to **@heygoodluck** for the report and the fix. (#261)
