## ✨ New: roles and multiple admin accounts

You can now create multiple admin-panel accounts and control what each one may do. (#222)

- **Settings → Users** — create accounts, assign a role, reset a password, or delete one. Click a username to open its detail panel: last sign-in time and IP, active sessions, the permissions the account actually holds, and every API token issued under it with its scope, expiry and last use.
- **Settings → Roles** — build a role by ticking read / write / delete per menu area (Proxy Hosts, Certificates, WAF, Logs, Settings, …). Three roles ship built in and cannot be edited: **Administrator** (everything), **Operator** (day-to-day work, no settings or account administration) and **Viewer** (read-only). Duplicate one to start a custom role from it.
- Menus a role cannot reach are hidden, and signing in lands on the first area the account can actually open. Hiding is a convenience — the server refuses the underlying request either way.
- **Read-only accounts see read-only screens.** Buttons an account may not use are disabled and say why, instead of failing after the click. When the server does refuse, the message names what was missing rather than showing a bare "Forbidden".
- **Role changes take effect immediately.** Restricting an account applies to its very next request; nobody has to sign out and back in.
- Accounts created by an administrator must set their own password before they can use the panel — the change screen cannot be skipped, and the temporary password stops working once it is changed.

Nothing changes for existing installs: your current account is migrated to the Administrator role, which keeps full access — including areas added in future releases.

## 🔐 Hardening that comes with multiple accounts

- **Sign-in lockout now counts per account as well as per IP.** Spreading guesses across addresses no longer avoids the lockout on the account being targeted.
- **Expired sessions are cleaned up on a schedule** instead of accumulating in the database.
- **Recovery still works when nobody can sign in.** `docker compose exec api ./server reset-password` finds administrators by role, so it keeps working on installs reorganised into custom roles.

### Notes for existing setups

- **API tokens are now capped by their owner's role.** A token can never exceed what the account that issued it may do, and it follows that account if its role is later restricted. Asking for more than the issuer holds is refused when the token is created, with a message naming the excess, rather than silently trimmed. Tokens with the "Full Access" scope are unaffected while their owner is an administrator.
- **Managing users and roles requires a Full Access token** over the API. Scoped tokens deliberately cannot create accounts or roles.
- Permission errors no longer echo the caller's own permission list back in the response.

## 📈 For operators who scrape `/metrics`

Unchanged from v2.33.5.

## 🔍 Known limitation

The API documentation at `/api/docs` is still reachable without signing in. Putting it behind a permission needs a different access mechanism than the bearer token the UI holds, so it is deferred rather than shipped broken.

> Pull the **api** and **ui** images and recreate:
> ```bash
> docker compose pull && docker compose up -d
> ```
