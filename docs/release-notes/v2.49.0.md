## 🛡️ WAF 자동 IP 차단이 이제 실제로 발동합니다

### ⚠️ 업그레이드 후 차단이 늘어날 수 있습니다

WAF 자동 차단을 켜 두셨다면, 지금까지 **거의 발동하지 않았을 가능성이 큽니다.** 업그레이드하면 설정하신 임계값대로 동작하기 시작하므로, 임계값이 의도보다 낮게 잡혀 있지 않은지 한 번 확인해 주세요.

무엇이 문제였는지 설명드립니다. 자동 차단은 "WAF 이벤트 수"를 센다고 안내했지만, 실제로는 **응답이 403이었던 이벤트만** 셌습니다. 그런데 차단 모드인 호스트라도 다음 경우에는 403이 아닌 응답이 나갑니다.

- 지오 차단을 **챌린지 모드**로 쓰는 경우 → 302 (CAPTCHA 페이지로 이동)
- 요청 수 제한에 걸린 경우 → 429
- 허용하지 않은 HTTP 메서드 → 405

이런 요청들도 WAF 규칙에는 분명히 걸렸는데 카운터는 0을 더했습니다. 개발 환경에서 확인해 보니 **차단 모드에서 발생한 실제 규칙 매치 4,424건이 카운터에 아무것도 기여하지 못했습니다.** 임계값이 5든 1이든 도달할 수 없는 상태였습니다.

이제 **"WAF가 차단 모드로 동작 중이었는가"** 를 기준으로 셉니다. 탐지 모드에서는 여전히 차단하지 않고(탐지는 관찰만 해야 하므로), 직접 제외 처리하신 규칙도 세지 않습니다.

## 🛡️ 전역 WAF를 상속하는 호스트가 조용히 탐지 모드로 바뀌던 문제

전역 WAF 설정을 **상속(inherit)** 하도록 둔 호스트에서, 아래 세 가지 중 하나만 해도 그 호스트의 WAF 설정 파일이 **자기 행에 남아 있던 옛 값**으로 다시 쓰였습니다.

- WAF 로그 화면에서 시끄러운 규칙 하나를 비활성화
- 전역 WAF 규칙을 켜거나 끄기 (이 경우 **모든 호스트**의 파일이 다시 쓰임)
- 백업 복원

그 결과 차단 모드로 보이던 호스트가 탐지 모드로 내려앉고, 다음번 전체 동기화 때 다시 돌아오는 현상이 생길 수 있었습니다. 이제 세 경로 모두 전역 설정을 반영한 실효값으로 파일을 씁니다.

**화면 표시도 함께 고쳤습니다.** WAF 목록과 상세 화면이 호스트에 저장된 값을 그대로 보여 주고 있어서, 상속 호스트가 실제로는 전역 설정(기본값: 탐지)으로 돌아가는데도 화면에는 **"차단"** 이라고 표시됐습니다. 운영자가 차이를 알아챌 방법이 없었습니다. 이제 실제로 적용 중인 설정을 표시합니다.

## 🌍 GeoIP 데이터베이스 갱신 후 국가 차단이 잠시 열려 있던 문제

GeoIP 데이터베이스를 새로 받으면 설정 파일이 실제 GeoIP 블록으로 교체되는데, **nginx를 다시 불러오지 않았습니다.** 그때까지 nginx는 이전의 "비활성 상태" 설정을 그대로 쓰고, 이 설정은 **모든 IP의 국가를 "알 수 없음"으로 만듭니다.**

국가 화이트리스트는 "알 수 없음"을 의도적으로 허용합니다(사설망 등을 막지 않기 위해서입니다). 그래서 데이터베이스 설치가 성공한 뒤부터 다른 이유로 nginx가 다시 불러와질 때까지, **한국만 허용하도록 설정한 호스트가 사실상 전 세계에 열려 있었습니다.**

이제 갱신이 끝나면 곧바로 nginx를 다시 불러옵니다. 실패하면 "이전 데이터베이스를 계속 사용 중"이라고 로그에 남깁니다.

## 🔢 잘못된 입력에 500 대신 400을 돌려줍니다

API가 "서버 내부 오류"라고 답하던 것들이 사실은 **입력을 고치면 되는 문제**였습니다.

- **인증 공급자 추가** — `type`에 허용되지 않은 값을 넣으면 데이터베이스 제약 위반 메시지가 그대로 나왔습니다. 이제 허용값을 알려 주는 400을 돌려줍니다.
- **DNS 공급자 추가/수정** — 자격 증명이 거부되면 Cloudflare의 응답 원문이 그대로 노출됐습니다. 이제 조치할 수 있는 안내와 함께 400을 돌려주고, 원문은 서버 로그에만 남습니다. Cloudflare에 **연결 자체가 실패한 경우**는 그대로 500입니다 — 장애를 "자격 증명이 틀렸다"고 안내하지 않기 위해서입니다.
- **지원하지 않는 DNS 공급자 종류** — 지금까지는 조용히 생성됐다가 인증서 발급 때 실패했고, 종류는 수정할 수 없어 삭제 외엔 방법이 없었습니다. 이제 지원 목록과 함께 즉시 거절합니다.
- **필터 구독 추가** — 구독 URL이 404를 돌려주거나 이름을 못 찾으면 "데이터베이스 오류"라고 표시됐습니다(데이터베이스는 관여하지도 않았습니다). 이제 원인을 알려 주는 400입니다.

## 🛡️ WAF auto-ban now actually fires

### ⚠️ Expect more bans after upgrading

If you have WAF auto-ban enabled, it has probably almost never fired. After upgrading it starts working at the threshold you configured — worth a quick check that the threshold is not lower than you intended.

Here is what was wrong. Auto-ban is described as counting "WAF events", but it only counted events whose response was **403**. A host in blocking mode still answers something else in these cases:

- Geo restriction in **challenge mode** → 302 (redirect to the CAPTCHA page)
- Rate limit → 429
- A disallowed HTTP method → 405

Those requests tripped WAF rules all the same, and the counter added zero for every one of them. On our development stack, **4,424 real rule matches in genuine blocking mode contributed nothing at all** — a threshold of 5, or even 1, was unreachable.

The counter now asks whether **the WAF was enforcing**, not whether the response happened to be 403. Detection mode still never bans (observing must not enforce), and rules you excluded still do not count.

## 🛡️ Hosts inheriting the global WAF could silently drop to detection mode

For a host set to **inherit** the global WAF settings, any one of these rewrote that host's WAF configuration file from **the stale values stored on its own row**:

- Disabling a noisy rule from the WAF log view
- Toggling a global WAF rule (this rewrites **every** host's file)
- Restoring a backup

A host that read as "blocking" could land in detection mode until the next full sync flipped it back. All three paths now write the effective, global-resolved settings.

**The display is fixed too.** The WAF list and detail views reported the host's stored columns, so an inheriting host showed **"blocking"** while actually running the global default (detection, by default). There was no way to notice. They now report what is actually in effect.

## 🌍 Country blocking was briefly open after a GeoIP database update

When a new GeoIP database is installed, the configuration switches to the real GeoIP blocks — but **nginx was never reloaded**. Until then nginx kept the previous "disabled" configuration, which resolves **every** address to an unknown country.

Country whitelists deliberately allow "unknown" (so private addresses are not blocked). The result: from a successful database install until some unrelated reload, a host restricted to one country was effectively open to everyone.

The update now reloads nginx immediately, and logs that the previous database is still in use if the reload fails.

## 🔢 Bad input answers 400 instead of 500

Several endpoints reported an internal server error for problems the caller can fix.

- **Creating an auth provider** — an out-of-enum `type` surfaced the raw database constraint message. It now answers 400 naming the allowed values.
- **Creating/updating a DNS provider** — rejected credentials echoed Cloudflare's raw response body. It now answers 400 with something actionable, and the upstream text stays in the server log. Failing to **reach** Cloudflare is still a 500, so an outage is never reported as bad credentials.
- **Unsupported DNS provider type** — previously created silently, then failed at certificate issuance; the type cannot be edited, so the row could only be deleted. It is now refused up front with the supported list.
- **Adding a filter subscription** — a URL that answers 404, or a host that does not resolve, was reported as "a database error" (the database was never involved). It now answers 400 with the reason.
