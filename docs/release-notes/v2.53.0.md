## 🚧 전역 Fail2ban — IP로 직접 들어오는 스캐너를 이제 차단할 수 있습니다

호스트별 Fail2ban에 실패 코드로 **444**를 넣어 두셨는데 아무 일도 일어나지 않으셨다면, 버그가 아니라 구조 때문이었습니다.

Fail2ban은 요청을 **어느 프록시 호스트의 것인지 확인한 뒤에** 실패를 셉니다. 그런데 `444`는 어느 호스트에도 맞지 않은 요청에만 나가는 응답입니다 — IP로 직접 접속했거나, 등록하지 않은 호스트네임으로 들어온 경우죠. 즉 세어질 수가 없었습니다.

**WAF → 전역 Fail2ban** 탭이 생겼습니다. 여기서는 바로 그 트래픽을 셉니다.

### ⚠️ 여기서 만든 차단은 모든 호스트에 적용됩니다

호스트별 차단과 성격이 다릅니다. 잘못 차단하면 사이트 하나가 아니라 **전부**에 영향이 갑니다. 그래서:

- **기본값은 꺼짐**이고, 처음에는 실제로 차단하지 않는 **"로그만 기록"** 으로 시작합니다. 며칠 로그를 보고 원하는 대상만 잡히는지 확인한 뒤에 차단으로 바꾸세요.
- **설정 → 신뢰 프록시를 먼저 지정해야 켜집니다.** 지정하지 않으면 모든 요청이 CDN이나 앞단 프록시의 주소로 보이고, 그 주소를 차단하면 그 뒤의 **모든 방문자**가 전 호스트에서 막힙니다. 켠 뒤에 신뢰 프록시를 지우시면 전역 Fail2ban은 스스로 동작을 멈추고 로그로 알려 드립니다.

### 세지 않는 것들

정상 방문자가 휩쓸리지 않도록 다음은 제외합니다.

- **리다이렉트 호스트로 등록하신 도메인.** 설정하신 호스트이므로 그 방문자는 스캐너가 아닙니다. 실제 로그 7일치를 보니 호스트에 연결되지 않은 404의 **100%**, 301의 **99.99%** 가 리다이렉트 호스트였습니다. 이 제외가 없으면 그분들이 전 사이트에서 차단됩니다.
- 형식이 깨져 어느 호스트로 온 요청인지 알 수 없는 것
- NPG 자체 점검 요청
- 루프백 주소와 신뢰 프록시로 지정하신 주소

### 기본 실패 코드는 실측으로 정했습니다

`400,444`입니다. 실제 로그 7일치로 시뮬레이션했을 때 오탐 0으로 스캐너 23개를 잡습니다. `403`과 `404`는 추가해도 잡히는 대상이 **늘지 않습니다** — 그 코드는 등록된 호스트에서만 나오기 때문입니다.

> 전역 Fail2ban을 켜신 뒤에는 **차단 IP 목록**을 한 번 확인해 주세요. 여기서 만들어진 차단은 호스트 표시가 없습니다.

## 🔧 API 명세 정정

`PUT /exploit-rules/{id}` 명세가 **생성용 스키마**를 가리키고 있어서, 명세로 클라이언트를 만들면 수정할 때도 `category`·`name`·`pattern`·`pattern_type`이 전부 필수라고 오해하게 됐습니다. 실제로는 바꾸실 필드만 보내시면 됩니다.

`category`는 수정으로 바꿀 수 없다는 점도 명세에 적었습니다. 지금까지는 보내도 **조용히 무시**되고 200이 돌아왔습니다. 카테고리를 바꾸시려면 삭제 후 다시 만드셔야 합니다.

## 🚧 Global Fail2ban — you can finally act on direct-IP scanners

If you put **444** in a host's fail codes and nothing ever happened, that was structural rather than a bug.

Fail2ban counts a failure only after matching the request to a proxy host. But `444` is only ever the answer to a request that matched **no** host — one that arrived by IP address, or with a hostname you never configured. There was nothing for a per-host jail to count.

**WAF → Global Fail2ban** is a new tab that counts exactly that traffic.

### ⚠️ Bans made here apply to every host

This is not the per-host jail. A false positive affects **all** your sites, not one. So:

- It **ships disabled**, with the action set to **"Log Only"**, which records without banning. Watch it for a few days, confirm only the traffic you want is caught, then switch it to blocking.
- **Settings → Trusted Proxies must be configured first.** Without it every request appears to come from your CDN or upstream proxy, and banning that address blocks **every visitor behind it** on every host. If you clear Trusted Proxies later, the global jail stops acting on its own and says so in the log.

### What it does not count

So that real visitors are never swept up:

- **Domains you configured as redirect hosts.** Those are your hosts and their visitors are not scanners. Across 7 days of real logs, **100%** of unattributed 404s and **99.99%** of unattributed 301s belonged to redirect hosts. Without this exclusion those people would be banned everywhere.
- Requests too malformed to tell which host they were for
- NPG's own self-checks
- Loopback, and any address you listed under Trusted Proxies

### The default fail codes were measured

`400,444`. Simulated against 7 days of real logs, that catches 23 scanning addresses with zero false positives. Adding `403` or `404` catches **nothing extra** — those codes only ever come from hosts you configured.

> After enabling it, take a look at **Banned IPs**. Bans from this jail show no host.

## 🔧 API specification corrections

`PUT /exploit-rules/{id}` pointed at the **create** schema, so a client generated from the spec believed `category`, `name`, `pattern` and `pattern_type` were all required on an update. In reality you send only the fields you want to change.

The spec now also records that `category` cannot be changed by an update — sending it was **silently ignored** and still answered 200. Change a rule's category by deleting and recreating it.

> Thanks again to **@four2mis** for the precise report. (#282)
